# Формат content pack

Content pack — нормализованный и готовый к загрузке результат импорта
оригинальной игры. Runtime и браузер не читают `.KN2`, `GAME.x`, RES или exe.

Текущая версия схемы: **0.1**.

## Сборка

```bash
# ВЕСЬ МИР — так собирают пак для игры (52 карты):
python -c "import os,re,subprocess,sys; n=sorted(int(re.match(r'(\d+)',d).group(1)) for d in os.listdir('project/maps') if re.match(r'\d+',d)); subprocess.run([sys.executable,'-m','knyaz2.content','build',*sum([['--map',str(x)] for x in n],[]),'--output','content_build'])"
python -m knyaz2.content verify content_build

# одна карта — только для быстрой проверки рендера, ИГРАТЬ НЕЛЬЗЯ:
python -m knyaz2.content build --map 19 --output content_build
```

**Пак с одной картой ломает игру.** Клиент строит список карт по манифесту, и
вход в любую другую локацию отвечает «карты нет в паке»: не открываются
деревни, не работают переходы, а встреча в пути молча отменяется — бой уходит
на отдельную карту-местность, которой в паке нет. Каталоги уже собранных карт
при этом остаются на диске, поэтому по содержимому `content_build/maps`
поломку не видно — смотреть надо `manifest.json`.

Сборщик читает редактируемые карты из `project/`, а графические ресурсы — из
установленной игры. Путь к игре по-прежнему задаётся переменной `KONUNG2_DIR`.

`content_build/` — generated-каталог. Сборка происходит во временной папке.
Существующая папка никогда не очищается, если в ней нет служебной метки
`.knyaz2-content-pack`.

**Публикация атомарна НЕ всегда.** Атомарна только ветка с переименованием
(`_publish`). Когда каталог уже существует, работает `_publish_in_place`, и он
копирует файлы ПО ОДНОМУ в алфавитном порядке. Пока копирование идёт, пак
рассогласован: `manifest.json` может быть от прошлой сборки, а `shared.json`
уже от новой, и `verify` в этот момент честно ругается на размер и sha256.
Отсюда правило: **не запускать `verify` и не играть, пока сборка не
закончилась**, а если `verify` ругается — сперва убедиться, что процесс сборки
завершён, и только потом искать настоящую поломку.

## Структура

```text
content_build/
  manifest.json
  maps/19/map.json
  assets/underlay/*.png
  assets/ground/*.png
  assets/terrain_overlays/*.png
  assets/objects/*.png
```

`manifest.json` содержит версию схемы, карты и SHA-256 каждого файла. Время и
локальные абсолютные пути в него не записываются, поэтому одинаковые исходники
дают одинаковый пакет.

## Карта 0.2 — сущностная

Документ карты собирается сериализацией доменной модели `konung2.world`, а не
пересборкой сырых таблиц. Верхние ключи:

```text
terrain   { ground[], overlays[], underlay{}, blocked[], daylit_cells[] }
buildings []      постройки со стенами: кадры, габариты, клетки, свет
props     []      всё остальное: деревья, заборы, мелочь
lighting  {}      когда движок включает локальный свет
coordinates, audio, daylight, hero, statistics, render_debug
```

**Сущность** — постройка или реквизит — несёт всё своё:

```json
{ "id": "legacy:19:building:9", "kind": "building",
  "record_slot": 9, "resource_slot": 420, "palette": 91, "state": 0,
  "position": {"x": 2447, "y": 906},
  "bounds": {"width": …, "height": …, "offset_x": …, "offset_y": …,
             "draw_x": …, "draw_y": …, "sort_height": …, "sort_bias": …,
             "sort_y": …},
  "frames": {"main": {"asset": "assets/objects/…png", "width": …, "height": …,
                      "offset_x": …, "offset_y": …}, "walls": …, "roof": …,
             "shadow": …},
  "lighting": {"main_static_palette": true},
  "cells": {"footprint": [[row, col]…], "floor": […], "routed": […]} }
```

* `frames` — кадры в порядке отрисовки движка (VA `0x425AA8`): `main`, затем
  содержимое здания, затем `walls`, последней `roof`. Все с одним якорем.
  `shadow` — не картинка, а спановая маска затемнения (VA `0x440788`).
* `bounds.sort_y` — готовый ключ глубины: высота большего из `main`/`walls`
  минус `sort_bias` (четверть высоты у построек с битом `0x08` hdr+0xFE).
* `lighting.main_static_palette` — бит `0x04` того же байта: кадр `main`
  блитится исходной палитрой (VA `0x425B0C`), поэтому **пол в доме не темнеет
  никогда**. Стены и крыша идут через пересчёт под сутки (VA `0x441393`).
* `cells` — клетки сетки самой постройки: `footprint` прячет крышу
  (VA `0x428282`), `floor` (бит 15) добавляет полупрозрачную копию игрока
  поверх сцены (VA `0x428900`), `routed` (бит 21) рисует юнита между `main`
  и `walls`.

**Земля.** Клетка несёт свои координаты, пару тайлов, готовый PNG и, если на
ней есть маска, локальный свет:

```json
{ "row": 32, "col": 22, "x": 2552, "y": 1024,
  "tiles": {"lower": 7, "upper": 20}, "asset": "assets/ground/7_20_none.png",
  "light": {"mask": 1, "glow": "assets/light/7_20_1.png"} }
```

`glow` — не готовый цвет, а **разность** «клетка с маской минус клетка без
маски»: клиент складывает её с кадром режимом `lighter`. При нулевой маске
разность равна нулю, поэтому у ауры нет тёмной каймы (см. FORMATS.md).

**Terrain** хранит общие свойства: `blocked` — непроходимые клетки (младшие 12
бит слова ненулевые, VA `0x4414A7`), `daylit_cells` — бит 22, юнит на такой
клетке блитится статичной палитрой (VA `0x425E81`), `underlay` — анимированная
подложка 256×256 (VA `0x428505..0x4288D4`), `overlays` — кадры GRAPH.RES из
первой 12-байтовой таблицы KN2 в исходном порядке (VA `0x42543D`).

Состояние NPC, предметов и квестов в карту не вшивается: это динамический мир
и сохранение, которое будет подключено отдельным слоем схемы.

## Девять миров одной карты

Жители, отряды, кучи и запись поселения зависят от того, за кого играют:
в оригинале это отдельный `GAME.<мир>` на героя. Поэтому карта несёт их
не списком, а словарём по слоту выбора — `units_by_world`,
`warbands_by_world`, `loot_by_world`, `village_by_world`, ключи `"0"…"8"`.
Слотов девять: шесть наших и четыре донорских минус общая Велиславна
(`konung2.donor.HERO_SLOTS`). Простые `units`, `warbands`, `loot`,
`village` остались запасными — их читают только паки, собранные до
девятки.

Какой мир достаётся слоту, решает `_world_of`: на картах своей игры —
родной мир героя, на чужих — общий (`NEUTRAL_WORLD`), а если общий на
этой карте безлюден, то нулевой.

**Расстановка проекта кладётся тремя слоями** (`scenario.json` карты):

```json
{ "units": [],                                    общее всем девяти
  "loot": [],
  "units_by_world": {"7": [ … ]},                 только своему слоту
  "loot_by_world":  {"7": [ … ]},
  "hide_by_world":  {"6": ["unit_866"]} }         убрать лицо оригинала
```

Второй и третий слой — место под сюжет отдельного героя: без них своя
расстановка встала бы перед всеми девятью, а чужое сюжетное лицо
оригинала нечем было бы убрать. Имя в `hide_by_world` — `unit_<номер>`,
как житель зовётся в паке.

## Своя погода

Канону погода неведома: в `KONUNG2.EXE` нет ни дождя, ни снега — ни строки.
Слой целиком наш, а закон снят с Diablo II (разбор в `docs/RAIN.md`).

```text
project/weather/<имя>/
  set.json     разметка кадров по РАЗМЕРАМ
  sheet.png    все кадры одним листом
```

От снаряда набор отличается одним: вместо восьми **направлений** у него
несколько **размеров**. У колец дождя это глубина — движок держит четыре
набора кадров, от крупного к мелкому, и берёт тем мельче, чем дальше кольцо
от зрителя.

```json
{ "name": "rain", "title": "Круги по воде", "sheet": "sheet.png",
  "blend": "additive",
  "sizes": [[{"x":0,"y":0,"width":91,"height":55,
              "offset_x":-45,"offset_y":-27}, …десять…], …четыре… ] }
```

Смешивание по умолчанию **сложением**, а не краской: в исходнике кольцо
нарисовано серой лесенкой (12…132), то есть оно подсвечивает то, что под
ним. Обычной альфой серое кольцо на тёмной земле выглядит грязным пятном.

Готовится командой из `d2extract`:

```bash
python tools/to_konung_weather.py --what rain
```

Собранный набор ложится в `shared.json` разделом `weather`, листы — в
`assets/weather/`. Клиент включает дождь флагом `?rain` (числом — густота
колец в секунду).

## Свои твари

Канон рисует тварь целым набором из `OBJECTS.RES`, и пород там ровно
тридцать. Чтобы поставить в игру существо, которого в игре нет, рядом с
проектом лежит слой своих наборов:

```text
project/creatures/<имя>/
  set.json     тело, масть, разметка кадров по позам и направлениям
  sheet.png    все кадры одним листом
```

`set.json` описывает себя сам:

```json
{ "name": "sorceress", "title": "Волшебница", "body": 200, "palette": "0",
  "sheet": "sheet.png", "sheet_size": [2048, 718],
  "poses": {"stand": [[{"x":0,"y":0,"width":28,"height":68,
                        "offset_x":-14,"offset_y":-64}, …], …восемь…], …} }
```

Позы — те же шесть, что у канона (`CREATURE_POSES`): `stand`, `walk`, `hit`,
`death_1`, `rise`, `attack`; направлений восемь, в порядке движка
`0=W 1=NW 2=N 3=NE 4=E 5=SE 6=S 7=SW`; кадр — прямоугольник на листе плюс
смещение верхнего угла от точки под ногами, ровно как у канонных наборов.
Больше восемнадцати кадров в направлении класть нельзя: столько держит
таблица анимаций движка.

Сборка (`_custom_creatures`) подшивает набор ПОСЛЕ канонных и мимо паспорта
кадров — тот считается по `OBJECTS.RES`, своего набора в нём нет, поэтому
кэш выпечки продолжает работать. Номера листов внутри набора свои, от нуля;
сборка сдвигает их на место в общем списке. Занятое канонное тело занять
нельзя — сборка остановится.

Клиенту разница не видна: он читает `creatures.sets` и не спрашивает, откуда
набор. Юниту на карте нужно поднять бит твари `0x40` в породе — иначе клиент
станет собирать его слоями человека из `HEROES.RES` и не найдёт ничего.

Тени у своих наборов нет: у канонной твари это отдельная маска спанов из
`OBJECTS.RES`, и брать её неоткуда.

## Эволюция

Версия 0.1 хранила плоский `objects[]` и четыре параллельных списка в
`collision`: чтобы собрать одну постройку, читателю приходилось соединять их
самому. Версия 0.2 отдаёт сущности целиком; правила живут в `konung2.world` и
переносятся в пак сериализацией, а не переписыванием. PNG по-прежнему
отдельные — перед атласами смысловая модель карты не изменится. Несовместимые
изменения повышают версию схемы; адаптер не должен молча принимать неизвестную.

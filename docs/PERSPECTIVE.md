# Перспектива Diablo II: закон, снятый с кода

Вопрос был такой: у нас чистая изометрия, и от этого не чувствуется объём, а
у Diablo объём есть — почему.

Ответ: **дело не в изометрии, она у нас почти такая же**. У Diablo поверх
изометрии включена настоящая перспектива, и это штатная опция игры, а не
свойство рисунка.

Величина её теперь известна ТОЧНО. Мерить кадры больше не нужно: перспективу
считает таблица в `Game.exe`, и она разобрана целиком.

> Прежняя редакция этого документа кончалась словами «работа не закончена,
> четыре метода разошлись» и просила снять чистую пару кадров. Пара не
> понадобилась: числа нашлись в самой игре.

## Ответ одной строкой

Масштаб растёт **линейно по экранной строке**, на одну единицу за 1635 строк:

```
масштаб(y) = 1 + (y − 171) · 0.00061158        (холст 800×600)
```

где `y` — строка кадра, а 171 — строка, на которой перспектива в точности
совпадает с плоской изометрией (ромб подклетки 32×16).

| | масштаб |
|---|---|
| строка 0 (верх кадра) | 0.895 |
| строка 171 | 1.000 |
| строка 470 (низ игрового поля) | 1.183 |
| строка 599 (низ холста) | 1.262 |

**Перспектива = 32 % по игровому полю и 41 % на весь холст.**

Горизонт (там, где масштаб обратился бы в ноль) лежит на 1464 строки ВЫШЕ
опорной, то есть далеко за верхним краем кадра. Поэтому схождения линий в
точку в Diablo не видно никогда — работает только пологий градиент.

## Где это лежит в exe

`Game.exe` версии 1.14d, image base `0x400000` (в 1.14 все `D2*.dll` слиты
в один файл, поэтому видеокод там же).

```
0x6DD56C  строка `.\Src\glPerspective.cpp` — имя модуля в assert'ах
0x50DC80  выделение буфера 0x8000 байт, указатель ложится в 0x880B6C
0x50DCD0  ПОСТРОЕНИЕ ТАБЛИЦЫ: 8192 записи по четыре байта
0x50DD50  задать начало отсчёта (0x880B60 / 0x880B68)
0x50DD60  МИР → ЭКРАН с перспективой
0x72F1DC  указатель на неё в таблице методов вывода
0x7C9138  ширина холста, 0x7C913C высота (наружу их отдаёт 0x5092F0)
```

Модуль нашёлся по строке имени исходника: `glPerspective.cpp` упоминается
ровно из двух мест — `0x50DC85` и `0x50DCAF`, это пара «выделить/освободить»
близзардовского распределителя памяти. Рядом с ними и лежит всё остальное.

## Таблица

Вся перспектива — одна таблица обратных величин (`0x50DCD0`):

```
для довода u от −4096 до 4095:
    table[u] = 3072000 / (clamp(u, −62537, 2999) − 3000)
```

Верхняя граница 2999 стоит только чтобы знаменатель не стал нулём. При `u=0`
выходит ровно −1024 — единица в формате 1/1024. Знак отрицательный, им же
разворачивается ось «поперёк».

Это чистое деление на расстояние до плоскости `u = 3000`, то есть
камера-обскура, а не приближение.

## Проекция

`0x50DD60`, для земли (высота 0):

```
глубина  = ((dx·24) >> 16) + ((dy·24) >> 16)      dx, dy — мир 16.16
поперёк  = ((dy·24) >> 16) − ((dx·24) >> 16)
множ.    = table[((глубина·724·886) >> 20) mod 8192]
экранX   = ((поперёк · множ. · 724) >> 20) + ширина/2
экранY   = (((−глубина·724 << 9) >> 10) · множ. >> 20) + высота/2 − 32
```

Константы узнаваемы и подтверждают модель камеры:

| число | доля от 1024 | что это |
|---|---|---|
| 724 | 0.70703 | cos 45° = 0.70711 — поворот изометрии |
| 886 | 0.86523 | cos 30° = 0.86603 — наклон камеры |
| 1228 | 1.19922 | 1.2 — множитель высоты (ось Z) |
| 3000 | — | расстояние до плоскости проекции |

## Два закона

Проверено прогоном самой арифметики движка (целочисленной, со всеми
сдвигами), а не подгонкой:

**Горизонталь — линейна по строке.** Наклон `+0.00061158` на точку, худшее
отклонение от прямой `0.00125`, то есть **0.12 %** на всём диапазоне. Это не
приближение, а следствие: обратная величина из таблицы, поделённая на
линейную глубину, даёт ровно прямую.

**Вертикаль — квадрат горизонтали.** Растяжение по вертикали равно
`масштаб²` (проверено длинным плечом: расхождение постоянное −4.7 %, и это
не форма, а выбор опорного шага плоского кадра). Так и должно быть у
наклонной плоскости под перспективой.

Отображение «плоская строка → перспективная» ложится дробно линейной
функцией с ошибкой **0.96 точки на 115 пробах**:

```
y = 2839145 / (1903.6 − f) − 1466.66
```

Полюс `f = 1903.6` и асимптота `−1466.66` — это тот же горизонт, что и в
линейном законе выше (171 − 1635 = −1464). Две независимые выкладки сошлись.

## Зависит ли от разрешения

**Наклон — нет.** Он собран из констант 724, 886, 24 и 3000, разрешения в
нём нет вовсе.

**Положение опорной строки — да.** Начало проекции стоит на `высота/2 − 32`,
а строка единичного масштаба на 97 точек выше него. Для 800×600 это 268 и
171; для 640×480 — 208 и 111.

Отсюда и общий размах: чем выше кадр, тем больше строк он захватывает и тем
сильнее разница между верхом и низом. Проценты выше названы для 800×600.

## Геометрия обеих игр

Мерено по данным, а не на глаз.

| | Diablo II | Князь 2 |
|---|---|---|
| ромб плитки пола | 160 в ширину | — |
| проходимая клетка | подклетка 32 × 16 (5×5 на плитку) | 58 × 32 |
| отношение | 2.00 : 1 | 1.81 : 1 |
| рост фигуры | 68 точек (волшебница) | 85 точек (герой) |
| рост к высоте клетки | 4.2 | 5.3 |
| ширина фигуры к ширине клетки | 0.88 | 0.85 |
| клеток в кадре | ~25 × 37 при 800×600 | ~26 × 28 |

Ширина плитки Diablo снята из `DT1`; отношение 2:1 подтверждается теперь и
кодом — ромб подклетки на опорной строке выходит ровно 32×16.

Вывод прежний: ни пропорция проекции, ни масштаб фигуры к земле, ни обзор
существенно не отличаются. Значит «нет объёма» — не про них, а про эти самые
32 %.

## Что это значит для нас

**Землю одну покорёжить нельзя.** Перспектива в движке лежит в самом
преобразовании «мир → экран», через которое проходят и юниты, и постройки, и
тени. Спрайты корёжатся вместе с землёй — это видно прямо в коде: другой
ветки для них нет.

Хорошая новость про цену: земля у нас **печётся одним холстом**
(`ground.js bake`) и кладётся в кадр одним `drawImage`. Раз масштаб линеен по
строке, укладывать можно полосами с постоянным шагом — внутри полосы ошибка
не превысит `0.0006 × высота полосы`, то есть при полосе в 8 точек это
половина процента. WebGL не нужен: набор аффинных полос ложится точно.

Спрайтам придётся пересчитывать и точку постановки, и масштаб той же
формулой, причём по вертикали — квадратом. Это и есть основная работа.

## Как это включить

**По умолчанию включена**, разброс 35 %. Снять — галочка «Перспектива» в
настройках (меню и то же меню внутри игры); срабатывает сразу при закрытии
меню, перезаход не нужен. Снятая возвращает ровно прежний кадр: обёртки сразу
зовут прежнюю отрисовку, `drawPlane` вырождается в тот же самый `drawImage`.

Это **единственная наша настройка, включённая вопреки правилу «без спроса —
как в оригинале»**: у движка проекция ортогональная. Решение осознанное,
объём того стоит; отключается одной галочкой.

Адресная строка оставлена для проверок и **перебивает настройку**:

```
?perspective=32     ровно как в Diablo на 800×600
?perspective=50     сильнее
?perspective=0      выключить, не трогая галочку игрока
&mesh=0             без сетки стен
&mesh=all           сетка всем кадрам постройки (первый заход, кривой)
```

Работает на любой карте, отдельной сборки не нужно.

## Устройство: камера отдаёт матрицу на строку якоря

Холст 2D перспективу выразить не умеет — `setTransform` только аффинное.
Зато вся сцена и так рисуется в мировых координатах через одну матрицу
камеры, и достаточно давать КАЖДОМУ содержимому свою, посчитанную по его
собственной точке на земле. Это `cameraApply` в
`knyaz2/web/static/perspective.js`; там же весь закон и больше нигде.

Правило деления физическое:

| что | как едет |
|---|---|
| плоскость: земля, вода, пятна света, **тени** | `drawPlane` полосами — горизонталь на масштаб, вертикаль сама выходит квадратом |
| всё стоящее: юниты, постройки, кучи, снаряды, листва, птицы | `withPerspective` по своей точке на земле, масштаб РАВНОМЕРНЫЙ |

**Якорь берётся на всю сущность, а не на отдельный блит.** Постройка — это
пол, стены и крыша тремя кадрами с разным нижним краем; дай каждому свой
якорь, и дом развалится. По той же причине птица едет за своей тенью, а
полупрозрачная копия юнита — за самим юнитом.

Правки по модулям:

| где | что |
|---|---|
| `perspective.js` | весь закон: `cameraApply`, `withPerspective`, `drawPlane`, обратный ход |
| `ground.js` | земля полосами, печётся с добавкой сверху |
| `scene.js` | вода плоскостью; герой, юниты, кучи, постройки — каждый своим якорем |
| `shadows.js` | маска копится плоско, кладётся полосами как земля |
| `light.js` | пятна света плоскостью |
| `projectiles.js` | снаряды, вспышки и огонь |
| `ambient.js` | листва и птицы |
| `units.js` | полупрозрачная копия юнита |
| `viewport.js` | крючки `setUnproject` (мышь) и `setViewExtent` (обрезка камеры) |

**Наклон задан разбросом, а не числом из exe.** У Diablo наклон 0.000612 на
точку при кадре в 600 строк; наш холст бывает вдвое выше, и тот же наклон
дал бы вдвое больше перспективы. Хранится разброс «низ к верху», наклон
пересчитывается под текущую высоту: `k = 2·разброс / ((2 + разброс)·высота)`.

## Проверено числами

* разброс по кадру **1.3500** при заказанных 35 % (профиль 0.870 → 1.000 → 1.175);
* прямой и обратный ход сходятся **точно** (невязка 0) — щелчок попадает
  туда, куда показывает картинка;
* середина кадра при включении не меняется: средняя разница яркости **1.6**
  против 43–68 у краёв, то есть искажение симметрично относительно камеры;
* за кадр **266 блитов** на главный холст, из них 55 под перспективой, и
  **ни одной** матрицы, разошедшейся со слоем сцены;
* кадр **16.8 мс** (p90 19.4) — шестьдесят в секунду держатся;
* с выключенным флагом selfcheck 17/17 и pytest 990.


## Постройка строит сетку себе сама

У Diablo есть глобальная сетка плиток, и каждая плитка дома знает свою клетку
на земле — оттого ближний край крыши и крупнее дальнего. У нас сетки нет: дом
лежит в любой точке и приезжает одной картинкой. Но **след дома мы знаем**
(`cells.footprint`), а значит можем построить сетку локально, из самого дома.
Включается вместе с перспективой, выключается `&mesh=0`.

**Глубина у дома меняется по СТОЛБЦУ, а не по строке.** Землю режем строками,
потому что у плоскости строка и есть глубина. С домом так нельзя: одна строка
содержит и верх дальней стены, и низ ближней. Зато у каждого экранного
столбца есть своя точка на земле — там, где стена этого столбца упирается в
грунт. Это нижняя кромка следа, форма у неё Λ: ниже всего в ближнем углу,
выше к боковым.

Поэтому режем **вертикальными полосами** (12 штук), каждой даём множитель по
её собственному основанию.

**И только СТЕНАМ.** Первый заход пускал через сетку все три кадра — пол,
стены, крышу, — и это была ошибка, видная сразу: дом корёжило. Линия
основания утверждает «у столбца x земля вот здесь», и для стены это правда,
она этим столбцом в грунт и упирается. Для крыши ложь: крыша накрывает весь
след, и в одном столбце у неё и ближний скат, и конёк, и дальний скат —
глубины разные, а модель всем выдаёт ближнюю. Крыша самая большая масса
дома, оттого и бросалось в глаза. Пол — та же плоскость, та же ложь.

Сейчас крыша и пол едут ровным множителем на всю постройку, стены — по
столбцам. `&mesh=all` возвращает сетку всем кадрам (для сравнения),
`&mesh=0` выключает совсем.

**Щелей нет по построению:** края полос берутся из общего непрерывного
отображения, правый край полосы i — это в точности левый край полосы i+1.
Проверено счётчиком узких разрывов: 1239 с сеткой против 1241 без (это
фоновый шум текстуры, новых не добавилось).

**Горизонталь считается от якоря дома, а не от оси камеры** — и это купленная
правка. Считал от оси: у столбцов разный множитель, в смещении появляется
добавка `(x − осьX)·Δмножителя`, и она растёт с расстоянием до оси. Постройки
у края кадра срезало наискось на сотни точек. Формально это схождение к точке
схода, и в настоящей проекции оно есть — но **наша земля его не имеет**:
она масштабируется построчно, горизонтали остаются параллельными. Дом
сходился, земля нет, дом и отрывался. От своего якоря добавка ограничена
полушириной дома: замер на 700 точках от оси — перекос упал с 44 точек до 17,
и от расстояния до камеры больше не зависит вовсе.

Что сетка убирает: промах основания о землю, **5.3 точки в среднем и 11.7
худший** по девяти домам Борья. С сеткой он ноль по построению — каждая
полоса садится на свою строку земли.

Цена: 270 блитов на кадр без сетки, 380 с ней.

Чего сетка не даёт: дальняя стена, спрятанная за ближней, попадает в те же
столбцы и получает её глубину. У Diablo это разные плитки. Видно только там,
где сквозь дом просвечивает, то есть почти нигде.

## Почему ближе к Diablo не подобраться

Разобрано по коду отрисовки, а не по догадкам. Вызовы проекции `0x50DD60`
идут **группами по четыре подряд**, и после каждого результат ложится в
структуру с шагом `0x1C`: `x, y, z, rhw=1.0, цвет, u, v`. Это вершина
Direct3D.

**Плитка у них не масштабируется — она натягивается текстурой на
четырёхугольник по четырём спроецированным углам.** Отсюда и сообщение
`Does not support perspective correct textures!` в exe.

У пола все четыре угла идут с `push 0` — высота ноль. У стены (`0x50D0A0`,
`0x50D0C9`) в проекцию уходит `z = h − 32` и `z = h`: **углы стены имеют
разную высоту**, то есть стена — вертикальный четырёхугольник в трёхмерии, и
перспектива делает из неё трапецию.

Сколько значит высота — замерено по таблице движка
(`tools/height_effect.py`): подъём на 128 точек даёт **+2.6 % масштаба**.
Веса в доводе таблицы почти равны: глубина 641464, высота 628736, то есть
подняться на единицу почти то же, что приблизиться на единицу.

Отсюда и предел. У Diablo дом — **геометрия**: у каждого угла известны и
место, и высота. У нас дом — **фотография коробки**: глубины у пикселя нет,
её приходится угадывать по следу. Угадывание верно для стен и неверно для
плоскостей. Полная точность требует не кода, а геометрии — то есть заново
собранных из кусков построек, чего у нас нет и не будет.


## Обрезка камеры

Перспектива сдвигает содержимое вниз: точка выше камеры подъезжает к ней,
ниже — уезжает. Значит половины вида перестают быть равными:

```
вверх = полвысоты / (1 − k·полвысоты)      видно ДАЛЬШЕ
вниз  = полвысоты / (1 + k·полвысоты)      видно БЛИЖЕ
```

При кадре 826 строк это 485 вверх и 359 вниз против плоских 413. Пока
`clampCamera` считал по плоской мерке, сверху открывались лишние клетки, а
нижний край карты становился недостижим — **и с него нельзя было выйти на
карту мира**. Теперь половины даёт `perspective.viewExtent` через крючок
`setViewExtent`; проверено: край карты ложится точно в крайнюю строку кадра,
запас ноль и сверху, и снизу.

По горизонтали шире всего у верхнего края (там множитель меньше единицы),
поэтому вбок берётся `полширины / масштаб_верха` — обрезка обязана держать
камеру так, чтобы за край карты не заглянуть нигде в кадре.

## Что остаётся за бортом

* интерфейс, полоса выбора и склейка слоёв — они экранные, и так и надо;
* ~~тень едет якорем хозяина~~ — **исправлено**: тень лежит НА ЗЕМЛЕ и едет
  по закону земли. Маска теней копится плоско, а перспектива накладывается
  один раз на всю маску при укладке (`drawPlaneScreen`, экранные полосы).
  Прежде тень ехала якорем хозяина, как спрайт: пока камера стоит, разницы

## Старые замеры по картинкам: чем кончились

Сохранено как урок. Пять методов дали пять ответов, и **ни один не был
надёжен** — сцена для фотограмметрии негодная: в кадре ходят люди, горят
факелы, а пол набран разными плитками и не периодичен.

| метод | ответ | вердикт по коду |
|---|---|---|
| автокорреляция одного кадра | не дал | повтора в полу нет, уверенность 0.06–0.40 |
| полосовое сравнение пары | 34.5 % и 8.9 % | **34.5 % оказался ближе всех** (истина 32 %) |
| гомография по земле | 1.53 | завышение в полтора раза; профиль торговался с аффинной частью |
| масштаб точек SIFT | ~1.05 | октавами такую разницу не разрешить |
| подбор заплатами | 1.24 и 1.90 | 1.24 близко, 1.90 мимо; разброс от НПС и факелов |

Что из прежних выводов **устояло**: перспектива есть только у трёхмерных
бэкендов (`Does not support perspective correct textures!`), на машине
разбора включена (`HKCU\...\Diablo II\VideoConfig\Render: 1`), искажение
чисто вертикальное, спрайты корёжатся вместе с землёй.

Что **отменено**: «общее увеличение в 1.15–1.20» — его нет. Перспектива
совпадает с плоской изометрией на строке 171 и расходится в обе стороны;
в среднем по игровому полю разница около 4 %, а не 15–20. И «линия глаза на
1059 точек ниже центра, поле зрения 32°» — это была арифметика по неверной
гомографии.

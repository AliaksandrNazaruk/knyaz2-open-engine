# Карта движка: как мы читаем konung2.exe

## Зачем

Мы переносим механику из оригинала, а не выдумываем свою. Пока единственным
инструментом был линейный дизассемблер по угаданному адресу, порт шёл так:
догадка → сборка → скриншот → «не то» → переделка. Каждая такая петля стоила
часы, а догадки успевали попасть в комментарии как факты.

Примеры цены: таблицу гнёзд читали как `(y, x, y, x)` вместо `(x, y, x, y)` —
предметы уезжали мимо ячеек; таблицу отрисовки читали двойными словами вместо
байтов — доспех и шлем вообще не появлялись на персонаже; девятую запись
панели считали «овалом оружия» — иконка падала в чужую кнопку.

## Что теперь есть

    engine/ghidra_project/     проект Ghidra (в репозиторий не идёт)
    engine/decompiled/         декомпилированный C (в репозиторий не идёт)
      index.json               все функции: адрес, размер, вызовы, ссылки
      functions/0x004xxxxx.c   код по функции
    engine/names.json          наши упоминания адресов — собирается из репозитория

Декомпилированный код — производное от чужого бинарника, поэтому лежит рядом,
но не коммитится. Наша аннотация (`names.json`) — коммитится.

## Чего Ghidra не находит сама

Функцию она заводит по `CALL`. Точку входа, на которую смотрит **только
указатель в данных**, автоанализ пропускает — и в `konung2.exe` это стоило
6.6% секции кода, причём ровно в тех местах, которые нужны порту:

    0x462E90   таблица обработчиков разговора, 76 указателей. Диспетчер
               0x435F44 прыгает по ней, ни одного CALL на обработчики нет —
               37 из 76 функциями не стали, и переносить действия было не с
               чего (обработчики 40, 44, 50, 64, 65, 70, 74, 75).
    0x42F22C   оконная процедура: единственная ссылка — поле lpfnWndProc
               структуры WNDCLASSA (VA 0x42EBD0). Там весь разбор сообщений
               и ввода; без неё, например, не видно, кто снимает загрузочный
               экран (FUN_0043A5CC вызывается только оттуда).

Их заводит `tools/ghidra/MakeMissingFunctions.java` — он идёт `-preScript`,
до анализа, чтобы автоанализ разобрал заведённое. Третьим проходом там общий
подметатель: все dword'ы инициализированной памяти, показывающие в секцию
кода мимо тела известной функции.

Проверить покрытие после прогона:

```bash
python tools/engine_map.py coverage
```

## Как пользоваться

```bash
tools/ghidra_decompile.sh              # полный прогон (первый раз, ~10 минут)
tools/ghidra_decompile.sh --reuse      # только выгрузка, без анализа

python tools/engine_map.py collect     # пересобрать карту наших упоминаний
python tools/engine_map.py info 0x425DB4   # что это за функция и где мы её трогали
python tools/engine_map.py refs 0x460FB4   # кто читает эту таблицу
python tools/engine_map.py search "0x5a"   # поиск по декомпилированному коду
python tools/engine_map.py todo            # крупные функции, которых мы не касались
```

## Правило

**В клиенте не появляется ничего, за чем не стоит адрес.** Каждое число,
таблица и правило в паке снабжаются ссылкой вида `VA 0x425DB4`, и эта ссылка
проверяется контрактным тестом против байтов игры (`tests/test_items_contract.py`).
Если в коде ответа нет — так и пишем «не найдено», а не подставляем
правдоподобное.

## Порядок разбора подсистемы

1. `engine_map.py search` по характерной константе или строке — найти функцию.
2. Прочитать её декомпиляцию целиком, а не окно вокруг адреса.
3. Выписать в `konung2/` правила с адресами в комментариях.
4. Контрактный тест: правило против байтов exe или против самих ресурсов.
5. Только потом — порт в клиент.

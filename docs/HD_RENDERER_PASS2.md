## 1. Проекция legacy → 3D: вывод и константы

### 1.1 Что дано

Из движка (`hero.js:201`, `shared.json → hero.direction_steps`):

```text
якорь клетки:  x = col·58 + (row нечёт ? 29 : 58);   y = row·16 + 16
восемь шагов:  W(−58,0) NW(−29,−16) N(0,−32) NE(29,−16)
               E(58,0)  SE(29,16)   S(0,32)  SW(−29,16)
```

Две диагонали — `e_SE = (29, 16)` и `e_NE = (29, −16)` — линейно независимы и
порождают всю решётку: `E = e_SE + e_NE`, `N = e_NE − e_SE`. Значит мир —
**плоская решётка, снятая одной аффинной проекцией**, и вопрос лишь в том,
какая ортокамера её даёт.

### 1.2 Вывод

Ортографическая камера, ось Z вверх, рыскание ψ, тангаж θ (наклон вниз):

```text
right = (−sin ψ,  cos ψ, 0)
up    = ( sin θ cos ψ,  sin θ sin ψ,  cos θ)
```

Для горизонтального вектора `P = (px, py, 0)`:

```text
экран_X      =  −px sin ψ + py cos ψ
экран_Y_вниз =  −sin θ · (px cos ψ + py sin ψ)
```

Возьмём ψ = 45°. Единичный шаг вдоль +y даёт `(L·0.7071, −L·0.7071·sin θ)`,
это направление NE = (29, −16). Отсюда система:

```text
L·cos 45 = 29           ->  L = 29√2 = 41.012193
L·cos 45·sin θ = 16     ->  sin θ = 16/29 = 0.5517241
```

**θ = asin(16/29) = 33.485377°.** Не 30° (учебная изометрия 2:1) и не
`atan(16/29) = 28.887°` — в первом отчёте стояло второе, исправлено.

Шаг вдоль +x при этом даёт (−29, −16) = NW, то есть **две перпендикулярные
оси 3D ложатся ровно на NE и NW**. Это и есть изометрия «по построению».

### 1.3 Константы

| Величина | Значение | Откуда |
| --- | --- | --- |
| yaw ψ | **45.000000°** | выбран; фиксирует NE/NW как оси решётки |
| pitch θ | **33.485377°** | `asin(16/29)` |
| sin θ / cos θ / tan θ | 0.551724 / 0.834027 / 0.661519 | — |
| L — мировых пикселей на 3D-единицу решётки | **41.012193** = 29√2 | `29 / cos 45` |
| вертикальный масштаб (высота) | **34.205263** px на единицу | `L·cos θ` |
| мир → плоскость | `u = X/58 + Y/32`, `v = X/58 − Y/32` | обращение базиса |
| плоскость → 3D | `(x, y, z) = (−u, v, h)` | из вывода выше |
| yaw модели по направлению | **`45° × ((dir + 5) mod 8)`** | проверено по всем восьми |
| орто-полуширина | `view.width / 2 / view.zoom / L` | в 3D-единицах |
| орто-полувысота | `view.height / 2 / view.zoom / L` | там же |
| центр камеры | `worldToPlane(view.cameraX, view.cameraY)` | — |

Высота снаряда `projectiles.js:71` = 30 мировых px = **0.8771 единицы**.

### 1.4 Ошибка — замерена

Прогон `scratchpad/proj.py`: по **200 000 случайных клеток** сетки (все 256×160
возможных плюс повторы) обратная проекция 3D → мировые пиксели сравнивалась с
`heroAnchor`.

```text
худшая ошибка: 1.819e-12 px
```

То есть **ошибки нет** — преобразование точное, остаток это двоичная точность
double. Легаси рисует в целых (`drawActor`: `Math.round(actor.x)`), поэтому
единственная реальная разница между картинками — это правило округления, а не
геометрия.

Цена ошибки в константе (поле обзора движка 884×708, полувысота 354 px):

| Наклон | sin θ | вертикаль | ошибка на краю поля | на 20 рядов (320 px) |
| --- | --- | --- | --- | --- |
| **asin(16/29) = 33.485°** | 0.551724 | ×1.00000 | **0.0 px** | **0.0 px** |
| 30° («изометрия 2:1») | 0.500000 | ×0.90625 | 33.2 px | 30.0 px |
| atan(16/29) = 28.887° | 0.483077 | ×0.87558 | 44.0 px | 39.8 px |
| 35.264° («истинная» изометрия) | 0.577350 | ×1.04645 | 16.4 px | 14.9 px |

Три десятка пикселей — это две клетки по вертикали: с таким наклоном юнит
стоял бы не в своей клетке.

### 1.5 Два следствия, которые иначе всплывут поздно

**Порядок глубины эквивалентен z-буферу — доказано.** Для точки на земле

```text
экран_Y_вниз = −L·sin θ·(px cos45 + py sin45)
глубина      =     cos θ·(px cos45 + py sin45)
глубина = −экран_Y · 0.036859        — строго монотонно
```

Значит **сортировка по экранному Y и z-буфер дают ОДИН порядок** для всего,
что стоит на земле. Расхождения возможны только там, где легаси добавляет
свою поправку: `−h/4` у построек с битом 0x08, `+6` у человека, «низ кадра» у
твари (`actor.js:45`, `geometry.py:137`). Это и есть готовый список мест, где
паритет надо проверять числом.

**Тайл земли смещён на 1 px.** Шаг решётки 116×32, а картинка тайла 114×64:
центр картинки на 1 px левее центра ячейки решётки (замерено на четырёх
тайлах, расхождение стабильно `(1, 0)`). HD-квады класть по решётке 116×32, а
не по размеру картинки, иначе шов поедет.

### 1.6 Если понадобится перспектива

`perspective.js` задаёт разброс `s` по кадру высотой `H`; `k = 2s/((2+s)H)`.
Эквивалентная настоящая камера:

```text
горизонт  = 1/k строк выше опорной
фокус f   = 1/(k·tan θ)
верт. FOV = 2·atan(H/2/f)
```

| Настройка | k на строку | горизонт | f | верт. FOV |
| --- | --- | --- | --- | --- |
| наш `SPREAD = 0.35`, кадр 600 | 0.00049645 | 2014.3 строк | 3044.9 px | **11.25°** |
| Diablo II, 800×600 | 0.00045977 | 2175.0 строк | 3287.9 px | 10.43° |
| наш `SPREAD = 0.35`, кадр 1080 | 0.00027581 | 3625.7 строк | 5480.9 px | 11.25° |

То есть «объём Diablo» — это **длиннофокусная камера с FOV около 11°**, а не
широкий угол. В 3D это одна строка настройки, и переключение орто ↔ перспектива
становится бесплатным.

### 1.7 Что писать в коде

```js
export const CAM = {
  yaw: Math.PI / 4,
  pitch: Math.asin(16 / 29),          // 33.485377°
  unit: 29 * Math.SQRT2,              // 41.012193 мировых px на единицу
};
export const heightPx = CAM.unit * Math.cos(CAM.pitch);   // 34.205263
export function worldToPlane(x, y) { return { u: x / 58 + y / 32, v: x / 58 - y / 32 }; }
export function planeTo3D(u, v, h = 0) { return { x: -u, y: v, z: h / heightPx }; }
export function yawOf(direction) { return (Math.PI / 4) * ((direction + 5) & 7); }
```

### 2.3 Предложение: один счётчик ревизии на ярус

Ничего не изобретаем и никуда не лезем — три числа в `world`:

```js
// world.js
export const world = { /* … */ revision: { map: 0, statics: 0, collision: 0 } };
```

* `revision.map++` — в `loadMap` (`world.js:87`);
* `revision.statics++` — в конце `questScriptApply`, `buildings.js` (после

* `revision.collision++` — в `heroStampBuilding` и `heroCellToggle`

Рендерер держит свои копии чисел и пересобирает ярус, когда число разошлось.
Двенадцать мест инкремента, ни одной строки игровой логики.

## 3. `GameplayPresentationEvent`

### 3.1 Что уже есть

В движке 19 одноместных слотов `world.on*` (замер: 19 объявлений, 21 точка
вызова у `onStatus`, 2 у `onUnitStrike`, …). Их уже оборачивает `agent.js:63
tapOne` — идемпотентно, помечая свою обёртку `__agentTap`, потому что вход на
карту слоты переназначает.

Проблема одна: **слот один**. Второй потребитель (рендерер) обязан либо
оборачивать, как агент, либо ждать своей шины.

### 3.2 Схема события

```cpp
struct GameplayPresentationEvent {
    uint64_t tick;          // clock.ticks — на нём рендерер и синхронизируется
    EventKind kind;         // strike | shoot | projectile_land | hit | death |
                            // spawn | despawn | object_state | cell_toggle
    uint64_t actor;         // кто сделал   (id юнита или record_slot объекта)
    uint64_t target;        // над кем      (0, если некому)
    Vec2     at;            // мировые пиксели точки события
    uint8_t  direction;     // 0…7 у актёра — рендереру нужен для доигровки
    uint16_t a, b;          // смысл по виду: рука (0 main / 1 off), урон,
                            // прежнее и новое состояние объекта, вариант смерти
};
```

Событие — **уведомление, а не запрос**: возвращаемое значение не используется
никем, обработчик не имеет права трогать мир. Это отличает его от
`world.onUnitStrike`, который сегодня и есть сам удар.

### 3.3 Точки испускания — все, поимённо

| Вид | Где испускать | Почему именно там |
| --- | --- | --- |
| `strike` | `units.js:2172` (`hand` из таблицы кадров) и `units.js:2221` (запасной удар в конце блока) | это единственные два места, где удар объявляется; оба уже зовут `world.onUnitStrike` |
| `shoot` | `combat.js:313-330` (ветка `rangedMode` обработчика) и `combat.js:884 heroStrikeWith` | тут рождается снаряд |
| `projectile_land` | `combat.js:1023` — колбэк `onHit` в `projectilesTick` | тут снаряд разрешается в урон |
| `hit` (вздрогнуть) | `units.js:1266 setPose(unit, "hit", true)` и `combat.js:629 heroSetPose("hit", true)` | обе ветки стоят сразу за списанием здоровья |
| `death` | `units.js:1202 die(unit)`, первая строка | и жребий варианта смерти рядом (`units.js:1225`) |
| `spawn` | `units.js:525 unitSpawn`, перед `return` | сюда же приходит засада `app.js:410` |
| `despawn` | `units.js:1210` (тело 15 исчезает), `mapTeardown` (`app.js:118`) | — |
| `object_state` | все строки таблицы §2.2 | заодно поднимает `revision.statics` |
| `cell_toggle` | `hero.js:303 heroCellToggle`, `hero.js:319 heroStampBuilding` | заодно поднимает `revision.collision` |

Итого **14 точек**, из них 5 уже содержат вызов хука — там добавляется одна
строка рядом.

### 3.4 Шина вместо слота

```js
// world.js — рядом с самим world, без новых зависимостей
const presentationSinks = [];
export function onPresentation(fn) { presentationSinks.push(fn); return fn; }
export function emitPresentation(event) {
  for (const sink of presentationSinks) { try { sink(event); } catch (e) { console.error(e); } }
}
world.emitPresentation = emitPresentation;      // как остальные ручки
```

Три свойства, ради которых это стоит писать именно так:

1. **Ноль влияния на канон.** Испускание идёт ПОСЛЕ того, как состояние уже
   изменилось; исключение в подписчике ловится и не рвёт такт (тот же приём,
   что `app.js:161 animationLoop` применяет к кадру).
2. **Не заменяет `world.on*`.** Старые слоты остаются как есть — их читают
   интерфейс, звук и агент. Новая шина — только для презентации.
3. **Пустая шина ничего не стоит:** цикл по нулю подписчиков.

### 3.5 Чего это НЕ решает

Событие даёт рендереру повод проиграть анимацию, но **не отменяет** того, что
темп боя задан длиной спрайтовой анимации (P0-3 первого отчёта). Пока
длительности блоков не вынесены в данные, HD-клип обязан длиться столько же
тактов, сколько кадров в легаси-блоке. Событие лишь избавляет рендерер от
необходимости угадывать момент удара по номеру кадра — а это и была цель.

## 4. Работает ли legacy picking без отрисовки — замерено

Прогон: локальный сервер `127.0.0.1:8765`, карта «Борье», 16 юнитов,
520 картинок (после `enterMap(33)` — 955 и четыре твари в кадре).

### 4.1 Проба не читает видимый холст — доказано

`units.js:1292-1296`: `probeCanvas` — **свой** холст 1×1 с
`willReadFrequently`; `unitPixelHit` рисует в него из `world.images`, то есть
из листа спрайтов, а не из кадра на экране.

Замер: видимый холст залит сплошным `#ff00ff` (проверено чтением пикселя —
`255,0,255,255`), после чего проба повторена по всем юнитам.

```text
попаданий до заливки:    11 / 11
попаданий после заливки: 11 / 11
результаты совпали:      да
```

**Вывод: выбор юнита не зависит ни от содержимого холста, ни от того, был ли
вызван `render()`.**

### 4.2 Листы к моменту клика уже есть

`app.js:805-810` — вход на карту ЖДЁТ `actorSheetPaths(map.hero, all)` **и**
`creatureSheetPaths([hero, ...all])`, то есть тела людей и наборы тварей всех
юнитов карты. Замер на четырёх тварях («Любница» body 14, «Марфа» body 14,
«Ярун» и «Глеб» body 15): `loaded: true` у всех.

### 4.3 Отсутствующий лист роняет не в прямоугольник, а на базовое тело

Замер: у живого юнита («Путята Медведь») из `world.images` удалён его лист
`hero_102.png`, проба повторена, лист возвращён.

```text
с листом:        попадание в тело — да, в прозрачную точку — нет
без листа:       ровно то же
```

Причина: `unitPixelHit` берёт кадр через `actor.js:392 actorBody`, а тот при
отсутствующем листе возвращает **базовый** кадр (и заодно заказывает
недостающий через `spriteReady`). Силуэт остаётся честным, теряется только
крашеный вариант.

### 4.4 Единственная настоящая дыра

`app.js:410` — засада с глобальной карты зовёт `unitSpawn`, а следом
`preload(mapAssets([]))`. `mapAssets` **не содержит листов актёров** (это
видно из его сигнатуры: они приходят аргументом `heroAssets`, здесь пустым).
Значит листы засадных юнитов заказывает только `spriteReady` во время
отрисовки. Без легаси-кадра они не будут заказаны никогда, и клик по такому
юниту выродится в прямоугольник 60×92 (`units.js:1287-1289`).

Лечится одной строкой в снимке или там же, в `app.js:410`:

```js
await preload([...actorSheetPaths(map.hero, newcomers),
               ...creatureSheetPaths(newcomers)]);
```

### 4.5 Ловушка вёрстки — замерена

| Как прячем | `getBoundingClientRect()` |
| --- | --- |
| видим | 100 × 50 |
| `display: none` | **0 × 0** |
| `visibility: hidden` | 100 × 50 |

`viewport.js:305 resize()` и `viewport.js:397 screenToWorld()` читают
`canvas.getBoundingClientRect()`. С `display: none` получаем `view.width = 1`,
и рушится всё сразу: `zoomFit`, `clampCamera`, краевая прокрутка, перевод
клика в мир. Значит:

> легаси-холст прячем **`visibility: hidden`** (или `opacity: 0`), сохраняя
> раскладку и размеры, — либо переводим `dom.js → canvas` на HD-холст, и тогда
> легаси-холст можно убирать совсем.

### 4.6 Вердикт

**Да, легаси-picking можно использовать при скрытом холсте и вообще без единой
отрисовки.** Условия ровно три:

1. холст остаётся в раскладке (`visibility: hidden`, не `display: none`) —
   либо `dom.js` смотрит на HD-холст;
2. листы юнитов, появившихся ПОСЛЕ входа на карту, заказываются явно (§4.4);
3. `selfcheck()` по-прежнему требует настоящей отрисовки — на время проверки
   паритета легаси-кадр надо включать (он и так остаётся эталоном).

## 5. WebGPU: что можно, что нельзя, и в каком порядке

### 5.1 Замер среды

Прогон в браузерной панели (Chromium 148 / Electron 42, **программный
растеризатор** — это среда инструмента, не боевая машина игрока):

```text
webgl2                 true
renderer               ANGLE (Microsoft Basic Render Driver, D3D11)
MAX_TEXTURE_SIZE       16384      (наши листы 4095x1709 — с запасом)
MAX_ARRAY_TEXTURE_LAYERS 2048     (листов всего 72 — массив текстур влезает целиком)
instancing             есть
EXT_float_blend        есть
anisotropic            есть
S3TC                   есть        ASTC — нет
OffscreenCanvas        есть
hardwareConcurrency    12
crossOriginIsolated    false      ← нет COOP/COEP, SharedArrayBuffer недоступен

navigator.gpu                    true
navigator.gpu.requestAdapter()   null        ← адаптера НЕТ
getPreferredCanvasFormat()       "bgra8unorm"
```

**Главный вывод из замера, а не из документации:** `navigator.gpu` бывает
истинным там, где адаптера не существует. Проверка обязана быть такой:

```js
const adapter = navigator.gpu && await navigator.gpu.requestAdapter();
const device  = adapter && await adapter.requestDevice();
if (!device) fallbackToWebGL2();          // и это НОРМАЛЬНЫЙ путь, а не ошибка
```

Гейт по `if (navigator.gpu)` дал бы в этой самой среде чёрный экран.

### 5.2 Ограничения сборки — из кода проекта

| Ограничение | Где | Что значит для рендерера |
| --- | --- | --- |
| **Сборщика нет вовсе** | нет `package.json`, нет `node_modules` | ES-модули отдаются сырыми. Библиотеку (three.js и подобные) можно только вкомпилировать одним файлом; проект живёт без единой зависимости — пишем сами |
| **Выкладка берёт ТОЛЬКО верхний уровень** | `tools/deploy_web.py`: «Только верхний уровень: подкаталог у клиента один», пропуск `menu/` | подкаталог `render3d/` **молча не уедет на сервер**. Все файлы рендерера — плоско в `knyaz2/web/static/` |
| **Рядом с файлом обязан лежать `.gz`** | там же, nginx `gzip_static` | забыл пережать — игрок получает старый файл. Уже наступали |
| **Кэш Cloudflare переживает смену заголовков** | память проекта, `docs/` | адрес версионируется через `content.js:19 contentUrl`; клиентские модули — нет, им поможет только пережатие и выкладка |
| MIME из `mimetypes.guess_type` | `server.py:4818` | `.wgsl` отдастся как `application/octet-stream`. Шейдеры держим **строками в JS**, а не отдельными файлами: и MIME не нужен, и лишних файлов в выкладке нет |
| `Cache-Control: no-cache` у стенда | `server.py:4828` | на разработке кэш не мешает |
| Тест импортов клиента | `tests/test_client_imports.py` | каждое импортируемое имя обязано быть экспортировано — новый модуль попадёт под проверку сразу |
| Пороги чистоты | `tests/test_client_hygiene.py` | мёртвый экспорт валит сборку в тот же день |

### 5.3 Решение

**WebGL2 для PoC, WebGPU для боевого — но не двумя рендерерами, а одним
рендерером над тонким швом.**

Обоснование, а не вкус:

* WebGL2 доступен везде, где вообще запускается игра, **включая среду без
  GPU** (замер выше: программный ANGLE работает, WebGPU-адаптера нет). Для
  PoC, где надо доказать совпадение геометрии, это решающее: PoC обязан
  запускаться у каждого, кто откроет ссылку;
* WebGPU даёт то, что нам действительно нужно **потом**, а не сейчас:
  bind-группы вместо цепочки `uniform`-вызовов, вычислительные проходы под
  частицы и смаз теней, честные инстансы для 7 000 тайлов;
* писать два независимых рендерера нельзя — они разойдутся, как разошлись три
  реестра каноничности (`CANON_AUDIT` против `CANON_PARITY_REVIEW_FINAL`).

### 5.4 Где проходит шов

Абстрагируем **ровно пять вещей** — меньше нельзя, больше вредно:

```text
RHI (тонкий, ~200 строк на каждый бэкенд)
  createTexture(image | array)      лист спрайтов / массив листов
  createBuffer(data, usage)         вершины, индексы, инстансы
  createPipeline(shaderId, state)   пара шейдеров + смешивание + тест глубины
  writeUniforms(name, data)         матрица камеры, уровни суток
  draw(pipeline, buffers, count)    инстансовая отрисовка
```

**Не абстрагируем** (и это важнее, чем что абстрагируем):

* язык шейдеров — держим две коротких пары (GLSL ES 3.0 и WGSL) рядом,
  один файл `shaders.js`, а не транслятор;
* сцену, камеру, снимок, сборку инстансов — они общие и от бэкенда не зависят;
* порядок проходов — он задан каноном кадра (`docs/RENDER_DEPTH.md`), а не API.

### 5.5 Порядок работ

| Этап | Что | Проверка |
| --- | --- | --- |
| 0 | `snapshot.js` + `worldToPlane`/`planeTo3D`/`yawOf` из §1.7 | юнит-тест на 200 000 клеток: ошибка < 1e-9 px |
| 1 | `render3d.js` на WebGL2: пол, стены, капсулы, орто-камера | F3 side-by-side: клетка под курсором совпадает |
| 2 | Ревизии ярусов (§2.3) и шина событий (§3.4) | стройка, квестовый OBJECT и открытие прохода видны в HD без перезахода |
| 3 | Инстансы тайлов, массив текстур, реальные спрайты как billboard | паритет глубины: знак `unitSortKey − sort_y` = знак z-разности |
| 4 | Шов RHI: тот же рендерер поверх WebGPU, выбор по `requestAdapter()` | оба бэкенда дают одинаковую картинку на одном снимке |
| 5 | Перспектива (§1.6) как переключатель камеры | сравнение с `?perspective=35` легаси |

На этапах 0–3 WebGPU не трогаем вовсе: пока геометрия не доказана, выбор API
ничего не решает.

декомпиляцией. Где что-то не проверено, это сказано прямо.

## 1. Само гнездо

Двенадцатое гнездо окна снаряжения, код мыши **0x1C**. Подсказка из exe:

> «Здесь можно смешивать волшебные снадобья и вкладывать волшебные камни в
> оружие или доспехи»

Гнездо вещь НЕ хранит: она всё время лежит там, где лежала, а гнездо только
помечает её словом `_DAT_00849668`. Помеченная ячейка мешка читается как
пустая (VA 0x420890). Ту же пару «вещь на вещь» разбирает и обычный щелчок в
любом окне (VA 0x421690) — гнездо просто удобное место.

**Где лежат вещи.** `FUN_0041DFE0` — общий перенос между блоками записи юнита:

    блок 5     -> юнит + 0x58    пять гнёзд снаряжения
    блок 0x2A  -> юнит + 0x62    мешок, 42 ячейки
    блок -5    -> юнит + 0xB6
    иначе      -> юнит + 0x50

Ячейки — массивы `short`, и в них лежат **номера записей предметов**, а не
сами вещи. Поэтому смена класса при варке ничего никуда не двигает.

Сами записи лежат подряд с **VA 0x6F956C, по 16 байт** — это видно по
переводу указателя в номер в хвосте `FUN_0041D954`:

```c
FUN_00423538(юнит, (запись - 0x6F956C) / 16, 0);
```

и по обращениям вида `(&DAT_006F956E)[номер * 0x10]` (байт +0x02 записи).

## 1а. Как вещь кладут и как берут

**Взять** — `FUN_0041DFE0(юнит, блок, номер)`. Для мешка (блок 0x2A) она не
просто гасит ячейку, а **сжимает** список: всё правее найденной переезжает на
ячейку влево, последняя обнуляется. Потом весь мешок (0x54 = 84 байта = 42×2)
копируется в снимок 0x8449EE, и туда же, в конец, дописывается номер взятой
вещи — это и есть «отмена переноса». Для гнёзд снаряжения проще: `*local_18 = 0`.

**Положить** — `FUN_00423538(юнит, номер, куда)`. Снято дизассемблером:

```asm
cmp dword ptr [ebp - 4], 0x2a          ; 42 ячейки
cmp word ptr [eax + 0x62], 0           ; ищем первое пустое
jl  ...                                 ; мешок полон -> вернуть 0
cmp dword ptr [ebp + 0x1c], 0
jl  без_сдвига                          ; ОТРИЦАТЕЛЬНЫЙ индекс — «куда влезет»
mov dword ptr [ebp - 4], 0x28           ; иначе идём с 40-й вниз до индекса
   mov ax,   word ptr [edx + 0x62]      ; мешок[i]
   mov word ptr [ebx + 0x64], ax        ; мешок[i+1]  — СДВИГ ВПРАВО
```

То есть **вставка со сдвигом**: указан индекс — всё от него и правее едет на
ячейку вперёд. Указано отрицательное — вещь просто ложится в первое
свободное. Дыр не остаётся: после сдвига движок снова ищет первое пустое и,
если оно оказалось левее заказанного места, кладёт туда.

Хвост той же функции чинит пометку гнезда смешивания: если помеченная вещь
(`_DAT_00849668`) не оказалась последней занятой, её меняют местами с
последней — чтобы пометка не уехала на чужую ячейку.

## 2. Запись предмета — все шестнадцать байт

Перечень снят перебором ВСЕХ обращений к массиву (`DAT_006F95xx`), а не по
догадке; в скобках — сколько мест читают поле.

| смещение | тип | что | кто |
|---|---|---|---|
| +0x00 | u8 | ВИД: 0 оружие, 9 снадобье, 0x0B камень, 0x0C боеприпас | 75 |
| +0x01 | u8 | четырёхбитная маска, разбирается `FUN_0041844C` — **не разобрано** | 4 |
| +0x02 | u8 | у боеприпаса: 0xFF чистые, **0** — намазаны маслом | 6 |
| +0x03 | u8 | КЛАСС (строка таблицы 0x45DAF0) | 98 |
| +0x04 | f32 | **концентрация** у снадобья, **прочность** у носимого | 28 |
| +0x08…+0x0B | — | обращений нет | 0 |
| +0x0C | u16 | заряд намазанной ОТРАВЫ | 7 |
| +0x0E | u16 | слово прибавок (чары); бит 0x8000 — «не опознано» | 12+21 |

Поля +0x0A у записи НЕТ: обращения вида `*(int *)(зап + 0x0A) >> 0x10` —
это чтение отравы +0x0C через int-сдвиг, любимую идиому этого кода.

Запись класса — 32 байта с VA 0x45DAF0: +0x00 название, +0x04 сила,
+0x08 прочность, +0x10 дальность, +0x12 цена (ЗНАКОВАЯ), +0x14 вес,
+0x16 значок.

### Где у юнита лежат вещи

| смещение | что |
|---|---|
| +0x50 | номер записи БОЕПРИПАСА (отдельное гнездо) |
| +0x58…+0x61 | ПЯТЬ гнёзд снаряжения, u16 каждое (+0x5A — стрелковое) |
| +0x62…+0xB5 | мешок, 42 ячейки u16 |
| +0xB6…+0xBF | ВТОРАЯ пятёрка гнёзд |

Обе пятёрки перебирает `FUN_0041C494`, и обе значатся в общем переносе
`FUN_0041DFE0` (блоки 5 и −5).

## 2б. Банки НЕ складываются в пачки

Слияние двух вещей в одну есть только у БОЕПРИПАСА. Снято дизассемблером
(`FUN_00421690`, ветка «уронить вещь на вещь»):

```asm
movsx eax, byte ptr [цель]              ; ВИД цели
cmp   eax, 0xc                          ; только 0x0C — боеприпас
jne   мимо
cmp   al, byte ptr [edx + 0x6f956f]     ; классы равны?
cmp   ax, word ptr [edx + 0x6f9578]     ; ОТРАВА равна?
mov   eax, [цель + 4]
add   eax, dword ptr [edx + 0x6f9570]   ; сумма счётчиков
cmp   dword ptr [ebp - 8], 0x1e
jg    переполнение
      mov [цель + 4], сумма
      mov byte ptr [eax + 0x6f956c], 0xff   ; роняемая УНИЧТОЖЕНА (байт вида)
переполнение:
      mov dword ptr [цель + 4], 0x1e        ; потолок пачки 30
      mov dword ptr [edx + 0x6f9570], сумма - 0x1e
```

Снадобья — вид 9, и до этой ветки они не доходят: `cmp eax, 0xc` их
отсекает. **Две банки одного зелья в мешке так и лежат двумя.** Единственное
их «сложение» — варка в гнезде, где складывается КОНЦЕНТРАЦИЯ, а склянок
всё равно остаётся одна (вторая становится пустой банкой или исчезает).

**Поле +0x04 записи используется ТРОЯКО** — и это, пожалуй, главная ловушка
формата:

| вид записи | что лежит в +0x04 |
|---|---|
| 0 (носимое) | прочность, `float` |
| 9 (снадобье) | концентрация, `float` |
| 0x0C (боеприпас) | счётчик пачки, `int`, потолок 30 |

## 2а. Слово прибавок: что даёт каждый бит

`FUN_0041C494` пересчитывает прибавки заново со всего надетого. Вещь
учитывается, только если она **опознана** — бит 0x80 байта +0x0F снят.

Слово +0x0E делится на пять групп по три бита, и у каждой своя таблица
значений (шаг 0x10, значение — знаковый `short` по +0x02 записи):

| группа | биты | маска | таблица | накопитель |
|---|---|---|---|---|
| броня | 12–14 | 0x7000 | 0x45D524 | 0x841CBC |
| удар | 9–11 | 0x0E00 | 0x45D584 | 0x841CC0 |
| ловкость | 6–8 | 0x01C0 | 0x45D5E4 | 0x841CA8 |
| сила | 3–5 | 0x0038 | 0x45D644 | 0x841CB4 |
| выносливость | 0–2 | 0x0007 | 0x45D6A4 | 0x841CB8 |

Уровень 0 не читается вовсе (`if (уровень != 0)`), значащие — с первого по
шестой, и это тот же потолок, что ставит камень:

| уровень | 1 | 2 | 3 | 4 | 5 | 6 |
|---|---|---|---|---|---|---|
| броня | +4 | +12 | +20 | +28 | +40 | +48 |
| удар | +4 | +12 | +20 | +28 | +40 | +48 |
| ловкость | +1 | +2 | +3 | +4 | +5 | +6 |
| сила | +1 | +2 | +3 | +4 | +5 | +6 |
| выносливость | +1 | +2 | +3 | +4 | +5 | +6 |

То есть камень брони и камень удара растут рывками (шестой уровень даёт +48,
вдвенадцатеро против первого), а три «характеристичных» камня — ровно по
единице за уровень.

### Как из базы получается текущее — и что делает байт +0x01

Хвост `FUN_0041C494`, снято с кода:

```c
for (i = 0; i < 6; i++) {
    if (накопитель[i] == 0)        знач = юнит[+0xC0 + i];          // одна база
    else if (0x8442F4[i] == 0)     знач = накопитель[i];             // ЗАМЕНА базы
    else                           знач = накопитель[i] + юнит[+0xC0 + i];
    если знач < 0 -> 0;
    юнит[+0xCC + i] = знач;
}
if (юнит[+0xD1] == 0) юнит[+0xD1] = 1;                               // пол Выносливости
```

Это и есть доказательство раскладки: **база +0xC0, текущее +0xCC**, шесть
штук. Байт +0xD1 — шестая текущая (Выносливость), и он принудительно не ниже
единицы; именно его читает формула скорости.

Накопитель — массив двойных слов с **0x841CA4**, и его поля ложатся ровно на
характеристики: +0*4 Харизма, +1*4 Ловкость (0x841CA8), +2*4 Интеллект,
+3*4 Обучаемость, +4*4 Сила (0x841CB4), +5*4 Выносливость (0x841CB8). Дальше
идут поля 7…9: 0x841CBC броня → юнит+0x42, 0x841CC0 удар → юнит+0x44,
0x841CC4 → юнит+0x46.

Это независимо подтверждает разбор слова чар из раздела 2а: три
«характеристичные» группы копятся ровно в те же ячейки, что и характеристики.

### Байт +0x01 записи предмета — особые свойства

`FUN_0041844C` разбирает его как **четырёхбитную маску**: цикл идёт по битам
8, 4, 2, 1 (`sar dword ptr [ebp - 4], 1` на каждом шаге), а при значении 0
или больше 15 — один проход с маской 0xFF.

Каждый взведённый бит адресует запись в 16 байт по `0x45D434 + бит*16`, и
запись — это ровно **три четвёрки** (функция читает поля `+0x434`, `+0x438`
и `+0x43C`, последние 4 байта записи не используются):

    +0  байт   НОМЕР накопителя, 1-based; ноль — конец списка
    +1  байт   маска
    +2  short  ЗНАЧЕНИЕ

Применение каждой четвёрки:

```asm
0x8442F4[номер-1] &= маска                 ; если ячейка ещё не ноль
если 0x8442F4[номер-1] != 0
     add dword ptr [номер-1)*4 + 0x841ca4], значение    ; ПРИБАВИТЬ
иначе
     mov dword ptr [(номер-1)*4 + 0x841ca4], значение    ; ЗАМЕНИТЬ
```

Снятая таблица:

| бит | что даёт |
|---|---|
| 1 | Харизма **+15**, Интеллект **+10** |
| 2 | Ловкость **−50**, броня **−100**, удар **−200** |
| 4 | накопитель 10 **+80** |
| 8 | Сила **+300** |

**Здесь я снимаю своё прежнее толкование.** Я писал, что +0x01 помечает
характеристики, которые вещь задаёт «наглухо». Ветка замены в коде есть, но
у ВСЕХ значащих записей маска равна **0x01**, а `FUN_0041C494` заполняет
0x8442F4 единицами — значит `x &= 1` ничего не обнуляет и ветка замены не
достижима. По факту байт +0x01 только ПРИБАВЛЯЕТ.

### …и всё это мёртвый код

Проверено по данным игры. Раскладка `GAME.N` снята с загрузчика
`FUN_0043D898`:

| смещение | что | размер |
|---|---|---|
| 0x00000 | **предметы**, 8192 записи по 16 | 0x20000 |
| 0x20000 | отряды | 0xC800 |
| 0x2C800 | постоянные контейнеры | 0x18A88 |
| 0x45288 | переходы | 0x109A |
| 0x46322 | юниты | 0x7D000 |
| 0xC3322 | | 0x378C |
| 0xC6AAE | | 0xA0 |

Сумма 0xC6B4E = **813902** — ровно размер `GAME.N` на диске; смещение юнитов
0x46322 совпадает с перемоткой, которую делает «новая игра». Два независимых
подтверждения раскладки.

Перебор всех шести миров: **у каждой без исключения вещи байт +0x01 равен
255**, то есть −1 со знаком. А `FUN_0041C494` читает его знаково и
отрицательные пропускает:

```asm
movsx eax, byte ptr [eax + 1]
test  eax, eax
jl    пропустить
```

Записей этого байта в движке нет вовсе — все четыре обращения к нему это
чтения в `FUN_0041C494`.

Значит `FUN_0041844C` не вызывается никогда, и таблица 0x45D434 в игре не
работает. Формат я разобрал полностью, но применения у него нет: это
задел, оставшийся в коде.

пустую банку. **Два одинаковых снадобья складывают концентрацию** — это и
есть режим 2, и он стоит у всех семи одинаковых пар.

### Пересчёт концентрации

Пять способов, потолок общий:

    0  конц = навык · 0.01
    1  конц = конц + навык · 0.01
    2  конц = своя + чужая
    3  конц = min(своя, чужая)
    4  конц = чужая + навык · 0.01
    затем: если конц > 15.0 -> 15.0

Шаг 0.01, потолок 15.0 — оба `double` в exe (0x4500F4, 0x4500FC, 0x450104,
0x45010C). Навык — двенадцатый, «Приготовление смесей», байт **+0xDE**
записи юнита, растёт на число из рецепта, потолок 100.

Результат кладётся в `float` +0x04 записи, поэтому считать надо в одинарной
точности.

## 6. Как концентрация показывается

`FUN_0043228B`, ветка описания вещи. Признак — **отрицательная цена** в
записи класса (знаковое поле +0x12):

```asm
mov eax, [eax + 0x45db00]; sar eax, 0x10; test eax, eax
jge пропустить
  strcat(буфер, ", концентрация ")
  fld dword [запись + 4]; sprintf(врем, "%5.2f", конц)
```

Минус стоит ровно у восьми варимых снадобий (85…92) — у остальных цена
обычная. **Цену этим классам движок не печатает вовсе**: ветка кончается
весом.

Ниже порога добавляется `", недостаточная концентрация"`:

    класс 87 «Масло»            — ниже 10.0
    класс 92 «Эликсир Мудрости» — ниже 6.0
    класс 93                    — ниже 10.0

## 7. Что делает выпитое и намазанное (`FUN_0041D954`)

Если цель — снадобье (вид 9), это варка. Иначе разбор по классу; классы
меньше 84 сюда не доходят вовсе.

Здоровье — `short` +0x4E, потолок **1600**; отрава — `short` +0x52;
таймер снадобья — `short` +0x4A.

Характеристик ТРИ набора, и снадобья работают с первым:

    +0xC0…+0xC5   БАЗОВЫЕ — их и меняет снадобье
    +0xC6…+0xCB   копия, снятая перед действием снадобья
    +0xCC…+0xD1   ТЕКУЩИЕ, с прибавками надетого
    +0xD2…+0xE5   двадцать навыков

Порядок в каждом наборе: 0 Харизма, 1 Ловкость, 2 Интеллект, 3 Обучаемость,
4 Сила, 5 Выносливость; потолок 150.

| класс | что делает |
|---|---|
| 84 Непонятная смесь | здоровье пополам, но не меньше 1 |
| 85 Лечебный бальзам | `доступно = (100 − здоровье/16)·0.1`, но не больше концентрации; `здоровье += доступно·160` (потолок 1600); `конц −= доступно` |
| 86 Яд | БЕЗ ЦЕЛИ: `отрава = round(отрава + конц)`. С ЦЕЛЬЮ вида 0 или 0x0C: `цель[+0x0C] = round(цель[+0x0C] + конц)`, и если вышел ноль, а конц ≥ 0.01, пишется единица |
| 87 Масло | требует конц ≥ 10.0 и цель вида 0x0C; ставит `цель[+0x02] = 0` |
| 88 Противоядие | `доступно = отрава·0.1`, но не больше концентрации; `отрава = round(отрава − доступно·10)`; `конц −= доступно` |
| 89 Брага | `N = min(базовая Ловкость / 3, конц)`; требует пустого таймера; сохраняет базовые в +0xC6; `+0x4A = N·30`; **Ловкость −3N**, Харизма +N, Сила +N, Выносливость +N |
| 90 Зелье | то же сохранение и таймер, но БЕЗ платы: Ловкость +N, Сила +N, Выносливость +N, и сверх того лечение до 1600 |
| 91 Чистая слеза | `N = round(конц)`; ставит `_DAT_00849610 = 1`; таймер `N·30`; пометка `+0xF8 = round(N · 0.1)`. Занятый таймер её НЕ останавливает — она просто не сохраняет базовые второй раз |
| 92 Эликсир Мудрости | `N = round(конц)`, требует **N ≥ 6**; таймер `N·60`; базовая Сила `= max(1, Сила − 5N)`; здоровье `-= N·160`, пол 160; опыт `= round((N − 5) · 100)` через `FUN_00413110` |

**Банка пустеет не всегда.** У Бальзама (85) и Противоядия (88) склянка
становится классом 83 только когда концентрация израсходована: условие
`конц ≤ 0.01`. У остальных — сразу. Значит одной сильной склянкой лечатся
несколько раз.

## 8. Отрава на оружии и стрелах

Заряд лежит в `u16` +0x0C записи ПРЕДМЕТА, не юнита. Намазать можно вид 0
(оружие) и вид 0x0C (боеприпас).

* **Расход**: каждый удар в ближнем бою убавляет заряд на единицу, если он
  не нулевой (`FUN_0041C194`: `если отрава != 0 -> отрава -= 1`); там же
  идёт износ оружия `сила · 0.00025`. У стрелкового резолвера расхода нет —
  выстрел стачивает лук.
* **Перенос в полёт**: сила и отрава кладутся в САМУ запись снаряда в миг
  выстрела (VA 0x41A52C), потому что бьют они в миг прилёта.
* **Слияние пачек**: две пачки боеприпаса сливаются в одну, только если
  совпадают и класс, и отрава; длина пачки не больше тридцати (VA 0x421690).

## 9. Масло: стрельба по объектам карты

Масло (класс 87) требует концентрации не меньше десяти и цели-боеприпаса.
Оно ставит **ноль** в байт +0x02 записи стрел — там, где у чистых стрел
0xFF. Урона это не меняет ни на единицу.

Что оно даёт на самом деле — **возможность взять на прицел ОБЪЕКТ КАРТЫ**, а
не юнита. Цепочка целиком:

**1. Курсор** (`FUN_00428B88`, это выбор курсора, а не поджог — прежняя моя
подпись была неточной). Курсор 4 выдаётся, когда под мышью объект
(`_DAT_00849534`) с битом 0x01 байта +0x22, и в отряде есть боец, у которого

    юнит[+0x19] & 0x04 != 0        боевая стойка
    юнит[+0xEE] == 1               стрелковый режим
    юнит[+0x5A] != 0               есть лук
    юнит[+0x50] != 0               есть боеприпас
    запись_боеприпаса[+0x02] == 0  ОН НАМАЗАН МАСЛОМ

**2. Приказ** (`FUN_00421690`). Щелчок по такому объекту при тех же условиях:

```asm
mov edx, 0x834744            ; база записей объектов карты
mov eax, [0x849534]          ; наведённый объект
sub eax, edx
idiv 0x24                    ; шаг записи объекта — 36 байт
neg edx                      ; ЦЕЛЬ = МИНУС НОМЕР
mov word ptr [юнит + 0x10], dx
mov byte ptr [юнит + 0x16], 0x61      ; «к цели», бит 0x20
mov byte ptr [юнит + 1], 0xff
and byte ptr [юнит + 0x19], 0xbf      ; снять бит 0x40
```

Отрицательное число в поле цели и значит «цель — объект»: хранится ровно
`−номер`. Читатель берёт `(−цель) − 1` и адресует таблицу от **0x834768**,
то есть от базы плюс одна запись, — итог сходится на нужном объекте.

**3. Исполнение** (`FUN_00410A08`, приказ 1):

```asm
mov eax, [юнит + 0xe]; sar eax, 0x10   ; цель — знаковое слово +0x10
test eax, eax
jge не_объект                          ; ОТРИЦАТЕЛЬНАЯ -> объект карты
cmp word ptr [юнит + 0x5a], 0          ; лук
je отказ
cmp word ptr [юнит + 0x50], 0          ; боеприпас
je отказ
neg eax; dec eax; imul eax, eax, 0x24  ; номер -> смещение записи
mov edx, 0x834768                      ; база + одна запись
... проверка бита 1 байта +0x22, затем FUN_00414AF8 (выстрел)
отказ -> FUN_00416E24, успех -> FUN_00416AC8 (поза стрельбы)
```

**4. Выстрел** (`FUN_00414AF8`). При отрицательной цели прицел берётся с
самого объекта: `0x834768 + номер*0x24` — его описание, дальше экранная
точка спрайта. Дальность считается по классу ЛУКА: поле +0x10 записи класса
(`0x45DAFE + класс*0x20`), а класс берётся из записи предмета `+0x5A`.

**Бит 0x01 байта +0x22 объекта** — это НЕ «горючесть», как я написал сперва.
Тот же бит проверяет отрисовка (`FUN_00425AA8`) прежде чем записать объект в
`_DAT_00849534`: он значит «объект ловится мышью и годится в цель».

**5. Прилёт** (`FUN_0041FDD0`, такт снарядов). Снаряды лежат с **0x833B08**,
шаг 32 байта, счёт `_DAT_008496A4`; байт +0x07 — срок жизни, на нуле снаряд
вычёркивается сжатием массива.

Каждый такт снаряд смотрит на ЦЕЛЬ СТРЕЛКА (слово +0x10 его записи). Если
она отрицательна:

```c
номер = -1 - цель;
если (нет поселения _DAT_00849538) или ((объект[+0x22] & 1) == 0)
    стрелок[+0x10] = 0;                    // цель снимается
иначе
    берём описание объекта, его маску и экранную точку
```

Дальше снаряд идёт восемью подшагами, и на клетке с битом **0x4000**
(преграда) проверяется попадание ПО ПИКСЕЛЯМ маски объекта
(`FUN_00442260`). Не попал — снаряд просто исчезает.

Попал — ищем объект среди ПОСТРОЕК поселения (снято дизассемблером):

```asm
mov  eax, [0x849538]          ; запись поселения
mov  dl,  byte ptr [eax]      ; число построек = [+0x00] + [+0x01] + 7
mov  al,  byte ptr [eax + 1]
add  edx, 7
add  eax, edx
mov  eax, [ebp - 0x48]        ; запись постройки, шаг 8 байт, с +0x18
mov  ax,  word ptr [eax + 2]  ; +0x02 — НОМЕР ОБЪЕКТА
cmp  eax, [ebp - 0x10]
jne  следующая
call 0x442b93                 ; бросок
idiv 0x64                     ; % 100
cmp  edx, 0x15
jge  мимо                     ; ЗАГОРАЕТСЯ ТОЛЬКО ПРИ БРОСКЕ < 21
mov  byte ptr [eax + 1], 3    ; СОСТОЯНИЕ ПОСТРОЙКИ = 3
mov  word ptr [eax + 6], 1    ; ТАЙМЕР = 1
```

**Итого: масляная стрела поджигает ПОСТРОЙКУ ПОСЕЛЕНИЯ с вероятностью 21 %.**
Урона объекту она не наносит вовсе — она переводит постройку в состояние 3.
Дальше та горит сама: мировой такт `FUN_0041C944` ведёт лестницу 3 → 6, на
каждой ступени убавляя таймер и вызывая `FUN_004171CC`, которая подменяет
описание объекта и переносит его флаги. Ступени 0…3 — это стройка, и она
требует работников; ступени 3…6 идут без них, по одному таймеру.

Отсюда и все условия цепочки: нужен объект, привязанный к постройке
поселения, — по одинокому дереву или чужому дому стрелять бессмысленно.

Стрела расходуется в любом случае: и при промахе по маске, и при неудачном
броске.

## 11. Чистая слеза (91) и Факел (46) — это СВЕТ

Обе вещи ставят один и тот же глобальный флаг `_DAT_00849610 = 1`
(`FUN_0041D954` case '[' и `FUN_00436C48` case '.'). Факел при этом **не
расходуется** — у его ветки нет `*param_3 = -1`.

Флаг меняет отрисовку объектов: и `FUN_00424514`, и `FUN_00424FD8` вместо
обычного затенения кладут блок `DAT_006A5598` размером 0x40 × 0x2B, центруя
его по объекту:

```c
if (_DAT_00849610 == 0)  обычная отрисовка с расчётным затенением
else                     FUN_0043FBDC(..., &DAT_006A5598, x - 0x20 + w/2,
                                      y - 0x15 + h/2, 0x40, 0x2B);
```

**Блок — это карта освещения из `LIGHTS.RES`.** `FUN_0043C228` открывает файл
и читает подряд: 0x1000 байт в 0x610010, **0xAC0 в 0x6A5598**, затем
девятнадцать блоков по 0x1C80. Сумма — 4096 + 2752 + 19 × 7296 = **145472**,
и это ровно размер `LIGHTS.RES` на диске, байт в байт.

Содержимое блока — эллиптическое пятно 64 × 43, значения 0…43 двадцатью
двумя ровными ступенями по 2, ярче к центру:

```
              ......::::::::......
        ..::::::::::----------::::::::::..
    ..::::----====++++++++++++++++====----::::..
  ::----==++++**####%%@@@@@@@@%%####**++++==----::
  ::----==++++**##%%@@@@@@@@@@@@%%##**++++==----::
    ..::----====++****##%%%%%%%%##****++====----::
        ......::::::------========------::::::
```

То есть это круг света, а не подменная картинка: Факел светит, Чистая слеза
даёт видеть. Флаг снимается только при загрузке карты (`FUN_0043DF48`);
таймер снадобья снимает лишь пометку +0xF8 у самого юнита.

## 11а. Применяемые вещи (вид записи 11)

Всё это разбирает один `switch` по КЛАССУ в `FUN_00436C48`. Навыки лежат
подряд с байта **+0xD2** (проверено независимо: навык 12 «Приготовление
смесей» = 0xD2 + 12 = +0xDE — ровно тот байт, что растит варка), потолок
сотня. Характеристики — с +0xC0, сохранённые копии — с +0xC6, потолок 150.

| класс | вещь | что делает |
|---|---|---|
| 30 | Вино | `N = min(базовая Ловкость / 3, **5**)`; если таймер пуст — сохраняет базовые; таймер = N·30; **Ловкость −3N**, Харизма/Сила/Выносливость +N; вещь исчезает |

### Вино — НЕ снадобье и к алхимии отношения не имеет

Похожесть Вина (30) на Брагу (89) обманчива: это разные вещи в разных
подсистемах. Проверено четырьмя независимыми способами:

| | Вино, класс 30 | Брага, класс 89 |
|---|---|---|
| вид записи | **11**, разбирает `FUN_00436C48` | **9**, разбирает `FUN_0041D954` |
| в книге рецептов 0x459FE4 | **0 строк** | **7 строк** |
| концентрация | нет — цена 100, положительная | есть — цена −4, отрицательная |
| предел прибавки | жёсткая пятёрка | сколько хватит концентрации |
| таймер уже идёт | молча перезаписывает | **отказ**, `return 0` |
| после применения | вещь исчезает | становится пустой банкой (83) |

Варка (`W_SFLB_mixmagics`) запускается только когда цель — запись ВИДА 9
(`if (*param_2 == '\t')`), поэтому Вино в гнезде смешивания не сварится ни с
чем. И `FUN_0041D954` вовсе не смотрит классы меньше 84 — Вина там нет.

Единственное, что у них общее, — ветка временных характеристик выглядит
похоже. Считаются они по-разному.

Имена сходятся со следствиями один в один и служат перекрёстной проверкой:
Гиппократ — знахарство, трактат о торговле — торговля, чертежи пирамид —
строительство, Третий Глаз — опознание, свиток кузнеца — кузнечное дело.

### Что это за два массива — КОНТЕЙНЕРЫ с мешком на 42 места

Запись 0x65 = 101 байт, и она раскладывается без остатка:

| смещение | что | чем доказано |
|---|---|---|
| +0x02 | отрицательная метка времени `-1 - такт/360` | `FUN_004136A8` |
| +0x05, +0x06 | строка и столбец (по ним гасится бит клетки) | `FUN_004136A8` |
| +0x08 | номер карты | сверка в зеркале с `_DAT_008496C8` |
| +0x0D | номер слота в постоянном массиве; отрицательный — «новый» | `FUN_0043A628` |
| +0x0B | спрайт кучи на земле (`FUN_0043BBC4`) | `FUN_0041F638` |
| +0x0F | **ДЕНЬГИ в контейнере**; отрицательные — клад ЗАРЫТ | `FUN_004115AC` |
| +0x11…+0x64 | **42 номера вещей — мешок контейнера** | цикл уничтожения `for (i=0; i<0x2A; i++)` |

Сорок два места по два байта с +0x11 — это 84 байта, и 0x11 + 84 = 0x65
ровно. Запись заполнена целиком, лишних полей нет.

**0x7AD7E4** — живой список текущей карты (счёт `_DAT_008496A8`),
**0x794D5C** — постоянный, тысяча записей, целиком уходит в сейв
(0x18A88 = 1000 × 101). При выходе с карты `FUN_0043A628` переписывает живые
записи в постоянные: если +0x0D отрицателен — заводит новую в конце, иначе
обновляет свою. Кончились слоты — вещи контейнера уничтожаются
(`(&DAT_006F956C)[номер*0x10] = 0xFF`).

**Трава отрастает.** `FUN_004136A8`, снимая живую запись, смотрит ПЕРВУЮ вещь
контейнера: если это вид 9 и класс **81 «Земляной орех»** или **82 «Белый
корень»**, слот не освобождается — в +0x02 ложится отрицательная метка
времени, а вещь заводится заново. Любая другая вещь — слот освобождается, и
счётчик подтягивается с конца.

То есть это и сундуки, и тайники, и грядки — один механизм на всё.

### Медное зеркало колдуна (класс 35)

Ветка `case '#'` перебирает ДВА массива записей по 0x65 байт:

```c
0x794D5C, счётчик 0x8496D0:   если байт +0x08 == текущая карта
                              и short +0x0F отрицательный -> сменить знак
0x7AD7E4, счётчик 0x8496A8:   если short +0x0F отрицательный -> сменить знак
```

Первый массив — тысяча записей (сохраняется целиком, 0x18A88 = 101000 =
1000 × 101) и живёт в сейве; байт +0x08 у записи это номер карты — то же
смещение, что у номера карты в записи отряда (`konung2/gamefile.py`).

Отрицательный `short` в +0x0F становится положительным.

**Читатель найден — `FUN_004115AC`, приказ 3 «обыскать».** Когда юнит дошёл
до контейнера:

```c
iVar3 = FUN_00442B7E(контейнер[+0x0F]);        // FUN_00442B7E — это abs()
*(int *)(_DAT_0084951C + 0x26) += iVar3;        // ДЕНЬГИ ИГРОКУ
*(short *)(контейнер + 0x0F) = 0;               // и обнулить
```

`+0x26` — деньги: та же ячейка правится торговлей на разницу цен
(`FUN_0041F638`, с зажимом в ноль) и уменьшается на 1200 в `FUN_00433818`.
Доказано движком, не нашими файлами.

**Минус значит «КУЧА СПРЯТАНА».** Знак поля +0x0F не имеет отношения к
сумме — при обыске она всё равно берётся по модулю. Он решает ВИДИМОСТЬ:
пока минус, куча лежит «под землёй», её не видно и не поднять.

Считать надо ПО МИРУ: мир — это отдельная игра, и раскладка у всех шести
одинаковая. **На одну игру: 342 кучи, из них 95 спрятанных, на 32 картах —
в среднем три на локацию.** Все спрятанные лежат на полу (байт +0x09 равен
0xFF), внутри объектов спрятанных нет ни одной.

Больше всего у «Волхва у Лесного лагеря» — пятнадцать; на прочих одна-три.
Всего в тайниках мира Ратибора **79 974 монеты**.

(Число 570 — это сумма по шести мирам, и приводить его как «сколько тайников
в игре» неверно: игрок видит только свой мир.)

Когда контейнер найден не приказом, а по клетке, ветка требует ещё одного:

```c
local_34 = FUN_004149F8(строка, столбец);
if (контейнер[+0x0F] < 0 && FUN_00434F8C(0x20) == 0)
    local_34 = 0;                               // обыскать НЕЛЬЗЯ
```

`FUN_00434F8C(0x20)` ищет в мешке игрока вещь класса 0x20 — **«Лопата»**.
То есть спрятанную кучу можно откопать, ткнув лопатой в нужную точку, даже
не видя её, — надо лишь знать место.

**А Медное зеркало колдуна переворачивает знак у всех спрятанных куч текущей
карты** — после него они просто лежат на виду, и лопата не нужна.

Свет (Факел, Чистая слеза) на это НЕ влияет: он подсвечивает то, что и так
лежит на земле, а спрятанное остаётся спрятанным — знак поля +0x0F и флаг
0x849610 никак не связаны.

Заодно в той же ветке: каждая неопознанная вещь в контейнере с вероятностью
«навык 15 из 100» опознаётся, и за каждую навык растёт на единицу.

### Вещи без ветки применения

В `switch` НЕТ классов **33 «Заячий хвост»**, **36 «Неразменный пятак»** и
**43 «Сын Луны»**. Щелчок по ним не делает ничего — значит работают они
иначе: либо весом и ценой (у «Сына Луны» вес −10000, то есть он облегчает
ношу, пока лежит в мешке), либо через разговоры и квесты.

**Не проверено**: где именно вступают в дело Заячий хвост и Неразменный
пятак. В таблице применения их нет — это установлено; чем они полезны, ещё
нет.

## 12. Чего в разборе ещё нет

* Попадание по объекту карты: горит он или просто получает урон.
* Картинка `DAT_006A5598` — что на ней.
* Поле +0x50 юнита в ветке Противоядия: там оно проверяется знаком
  (`юнит[+0x50] >> 0x10 < 0` обнуляет отраву), а здесь это номер записи
  боеприпаса — совпадение смещений надо перепроверить.

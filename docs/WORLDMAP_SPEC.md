# Глобальная карта: скорость похода и встречи

Дата разбора: 2026-08-10. Повод — отчёт тестера: «по карте мира перемещение
слишком быстрое, в оригинале скорость зависит от уровня навыка Следопыт».

Всё ниже снято с `konung2.exe`. Навык 13 «Следопыт» — байт **+0xDF** записи
юнита (навыки идут подряд с +0xD2, проверено независимо: навык 12
«Приготовление смесей» = +0xDE, его растит варка).

## 1. Скорость похода — `FUN_00421690`, щелчок по карте мира

```c
// расстояние — ЧЕБЫШЕВСКОЕ: большая из двух проекций
iVar4 = abs(dx);
_DAT_008496C0 = (iVar4 < abs(dy)) ? abs(dy) : abs(dx);

// ЛУЧШИЙ СЛЕДОПЫТ В ОТРЯДЕ, а не у игрока
local_18 = 0;
для каждого юнита отряда:
    если local_18 < юнит[+0xDF] -> local_18 = юнит[+0xDF];

_DAT_00849568 = ((100 - local_18) * 0.01 + 1.0) * _DAT_008496C0;
_DAT_00849564 = dx / _DAT_00849568;      // шаг по X за такт
_DAT_00849568 = dy / _DAT_00849568;      // шаг по Y за такт
_DAT_008496C0 = ROUND(...);              // счётчик тактов пути
```

Константа `0.01` — `float` по **0x45049E**.

**Делитель = (100 − навык) · 0.01 + 1.0**, и он же множитель числа тактов:

| Следопыт | делитель | во сколько дольше идти |
|---|---|---|
| 0 | 2.00 | вдвое |
| 25 | 1.75 | |
| 50 | 1.50 | в полтора раза |
| 75 | 1.25 | |
| 100 | 1.00 | предел скорости |

То есть навык ускоряет поход **ровно вдвое** между нулём и сотней, не
больше. Скорость задаётся не длительностью, а ШАГОМ ПО ОСЯМ: `dx/делитель`
и `dy/делитель` за такт. Если двигать отряд постоянным шагом, поход выходит
всегда самым быстрым — это и есть наша ошибка.

**Навык берётся ЛУЧШИЙ ПО ОТРЯДУ.** Перебор идёт по числу юнитов отряда
(`_DAT_0084950C[+0x19]`), начиная с игрока, шагом 0x100.

## 2. Случайные встречи — `FUN_004277F4`, такт глобальной

```c
если ((DAT_0084962C & 0xF) == 0)            // раз в шестнадцать кадров
   && ... условия по клетке ...
   && (rand() % 100 > игрок[+0xDF])          // БРОСОК ПРОТИВ СЛЕДОПЫТА
{
    открыть ENCOUNTS.RES, собрать встречу
}
```

Здесь навык берётся **только у игрока**, а не максимум по отряду — в
отличие от скорости. Работает как защита: бросок из ста должен ПРЕВЫСИТЬ
навык. При Следопыте 100 случайных встреч не бывает вовсе, при нуле они
возможны на каждой проверке.

Период проверки — тот же счётчик кадров и та же маска `& 0xF`, что у отравы
(VA 0x41C944), то есть раз в шестнадцать кадров.

## 3. Чего в разборе нет

* Прочие условия встречи (три сравнения по клетке перед броском) не
  разобраны — сняты только маска периода и сам бросок.
* Как расходуется игровое время в походе и где тикает отрава на глобальной
  (VA 0x4277F4 её тоже трогает) — отдельная работа.

## 4. Что чинить в клиенте

1. Ход по карте мира должен делить шаг на `(100 − лучший Следопыт) · 0.01 + 1`.
2. Расстояние — чебышевское, `max(|dx|, |dy|)`, а не евклидово.
3. Порог случайной встречи — `rand() % 100 > Следопыт игрока`, раз в
   шестнадцать тактов.

## 5. НОМЕР КАРТЫ ЗА ПРЕДЕЛАМИ КАНОНА

Читать это ДО того, как заводить новую карту или новую локацию. Порт берёт
кучу канонных данных таблицами, у которых индекс — номер карты, и таблицы
кончаются там, где кончается канон. Границы у них не подписаны: за концом
сразу лежит следующая таблица, и чтение молча возвращает чужие байты,
похожие на правдоподобные значения.

### Какие номера уже заняты

| диапазон | чем занят |
|---|---|
| 1…54 | карты игры (52 штуки, номеров 4 и 5 нет) |
| 100…146 | отряды в `GAME.<мир>`: бродячие по глобальной и встречные |
| 147…255 | свободно |

Правило проекта: карта, перенесённая из «Продолжения легенды», получает
номер `150 + номер у донора`. Все 90 донорских карт умещаются в 150…249 и
влезают в байт номера локации.

Проверять занятость надо по ЖИВЫМ записям отрядов, а не по списку карт:

```python
from konung2.gamefile import map_parties, map_units, map_exits, map_events
busy = any(map_parties(n, w) or map_units(n, w) or
           map_exits(n, w) or map_events(n, w) for w in range(6))
```

### Границы таблиц

Каждая посчитана по расстоянию до следующей таблицы, а не назначена:

| таблица | VA | записей | конец упирается в |
|---|---|---|---|
| постоянное освещение | `0x4617B0` | 55 (`FIXED_LIGHT_COUNT`) | таблицу указателей |
| прибытия на карту | `0x460028` | 55 (`ARRIVAL_COUNT`) | сетку мира `0x460174` |
| значки локаций | `0x4615CC` | 44 (`MARKER_COUNT`) | имена локаций `0x4616D4` |

Все три когда-то читались без границ, и все три давали не ошибку, а тихий
мусор. Освещение: карта 156 брала из соседней таблицы указатель `0x00451F26`
и раскладывала его на уровни — синий 38, зелёный 31, красный 69, — отчего
вся сцена заливалась розовым. Прибытия: читалось 64 записи вместо 55, и
карты 56, 58, 60, 63 получали место прибытия, вычитанное из сетки мира.
Значки: гнёзд локаций 55, а значков 44, и локация с номером за 44 брала бы
свой значок уже из таблицы имён.

Договор закреплён в `tests/test_worldmap_contract.py`: тесты сверяют каждую
границу с расстоянием до следующей таблицы и падают, если её сдвинут.

## 6. УГОЛ СЕТКИ: ЭКРАН ИЛИ КАРТИНКА

Движок рисует карту мира в окне мира и отсчитывает сетку от левого края
**экрана**: `ORIGIN_X = 0xA7 = 167`. Но окно мира начинается со столбца 140
(ширина левой панели), а сама картинка карты — спрайт 4 INTERF.RES — это и
есть окно мира, 884x709. Значит внутри картинки сетка начинается с 27, а не
со 167.

Клиенту панели нет вовсе: ему карта приходит картинкой, и у нарисованной
карты 1404x952 никакого «окна мира» нет. Поэтому **угол пересчитывается один
раз, при сборке пака** — `knyaz2/content/worldmap.py`, — и в пак едет уже
координата внутри картинки.

### Чем это обернулось

Клиент перевели на новый договор, а пак, которым играли (`content_build`),
остался собранным по старому. Ошибки не случилось ни одной: карта осталась
канонной 884x709, а сетка, туман и **все значки локаций уехали вправо на
140 точек**, часть их вылезла за край холста. Со стороны это выглядит как
«карта размером с оригинал, а деревни не на своих местах», и по виду не
угадать, что виноват не расчёт, а несобранный пак.

Заодно разъехалось то, что раньше друг друга гасило: щит своего отряда
рисовался со сдвигом на панель ВЛЕВО, а щелчок «войти» и цель похода — на
панель ВПРАВО. При экранном угле это сходилось, при картиночном — нет.

### Как теперь отличают одно от другого

Проверкой, а не догадкой: **сетка обязана умещаться в картинку.**

| угол | занимает | картинка | умещается |
|---|---|---|---|
| экранный 167 | 167 + 32·26 = 999 | 884 | нет |
| картиночный 27 | 27 + 32·26 = 859 | 884 | да |
| расширенная 0 | 0 + 54·26 = 1404 | 1404 | да |

Проверка стоит в двух местах: `knyaz2/content/worldmap.py` не даёт **собрать**
пак с экранным углом, а `originInPicture` в `knyaz2/web/static/worldmap.js`
чинит **старый** пак на лету. Ширину панели во всём клиенте знает только эта
функция; в коде карты мира её быть не должно, и это проверяет тест
`TestClientKeepsOneCoordinateSystem`.

**Меняя договор между паком и клиентом — пересобери пак, которым играют.**
Несовпадение здесь не падает, а тихо съезжает.

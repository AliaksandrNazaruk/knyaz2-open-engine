# Архитектура открытого движка Knyaz2

Этот документ фиксирует целевую архитектуру проекта. Исторические планы
исследований остаются в `PLAN.md`, `OPEN_ENGINE.md`, `HOOK.md` и `FORMATS.md`,
но новые технические решения должны сверяться с этим документом.

## Цель

Создать понятный открытый движок «Князя 2» на Python, который:

* импортирует данные установленной оригинальной игры;
* исполняет игровую логику без `konung2.exe`;
* не зависит от способа отображения и ввода;
* запускается headless, через сервер или непосредственно в браузере;
* предоставляет версионированный API для модов.

Это не построчная реконструкция исходников оригинального exe. Мы строим
поведенчески совместимый движок по форматам, наблюдениям и проверяемым
экспериментам, но с нормальными именами, типами и границами модулей.

## Главная граница

Ядро получает команды и возвращает события со снимком состояния:

```text
адаптер ввода -> Command -> HeadlessEngine.step()
                                |
адаптер вывода <- Events + WorldSnapshot
```

Ядро не знает, откуда пришла команда и кто читает результат. Обычный вызов
Python, WebSocket и `postMessage` Web Worker используют один протокол.

## Слои

### `knyaz2.core`

Владение состоянием мира, игровой такт, проверка команд и публикация событий.
В этом слое запрещены зависимости от DOM, графики, звука, сети и конкретного UI.

На переходном этапе `HeadlessEngine` использует готовую `simulation/`. Логика
переносится внутрь нового пакета постепенно и только вместе с тестами.

### `knyaz2.protocol`

JSON-совместимые команды, события и снимки. Это публичная граница для
браузера, headless-прогонов и будущего SDK модов. Изменения протокола должны
быть версионированы.

### `konung2` (будущий `knyaz2.legacy`)

Кодеки оригинальных `.KN2`, `GAME.x`, `QUESTS.RES`, ресурсов и exe-таблиц.
Их задача — импорт, экспорт и проверка совместимости, а не исполнение игры.

### Content compiler

Отдельный инструмент один раз превращает установленную игру в нормализованный
пакет карт, таблиц, атласов и звука. Браузер не должен разбирать многомегабайтные
оригинальные RES-файлы при каждом запуске. Текущая схема описана в
`CONTENT_PACK.md`.

### Адаптеры

* headless — тесты, симуляции и воспроизводимые прогоны;
* server — CPython-ядро и транспорт для браузера;
* web — камера, ввод, Canvas/WebGL, звук и интерфейс;
* pyodide worker — тот же Python-пакет локально в браузере без сервера.

Адаптер может переводить мировые координаты в экранные, но не меняет мир сам.

## Инварианты ядра

1. Мир меняется только через команды и системы игрового такта.
2. Один seed и одна последовательность команд дают один результат.
3. Координаты ядра — клетки и мировые единицы, не пиксели экрана.
4. Снимки, команды и события сериализуются без Python-объектов UI.
5. Статический контент отделён от динамического состояния сохранения.
6. Любое восстановленное правило оригинальной игры получает тест или fixture.
7. Мод не должен патчить внутренний список или бинарное смещение ядра.

## Текущий переходный API

```python
from knyaz2.core import HeadlessEngine
from knyaz2.protocol import Command

engine = HeadlessEngine.from_world(world)
result = engine.step([Command.move("player", row=10, col=12)])

payload = result.to_dict()  # можно отправить в браузер как JSON
```

Первая версия возвращает полный динамический снимок после каждого такта.
Когда состояние станет большим, протокол получит дельты, не меняя модель команд.

## Правило миграции

Глобальная переделка идёт вертикальными срезами:

```text
исследовать -> описать -> протестировать -> перенести в ядро
             -> сравнить с оригиналом -> показать в браузере
```

Мы не ждём полной декомпиляции всей игры перед первым запуском. Каждый
перенесённый срез должен быть играбелен и оставлять репозиторий рабочим.
